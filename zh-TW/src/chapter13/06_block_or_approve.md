# 什麼時候該擋、什麼時候可以放行

## 本集目標

review 一個 PR 時，用同一套標準決定每一則意見是擋還是放行：合併後會出錯、卡住、被攻擊，或難以回頭的，擋；風險低、之後改的成本也低的，核准並附意見，後續用 issue 追蹤；個人偏好不擋。

## 情境

候補名單 PR 收到 R1～R7 七則意見，reviewer 要決定這個 PR 能不能合併。R1 是遞補寫在 handler，本章〈[先看設計，再看細節](01_design_before_details.md)〉談過；R2～R7 各自對應檢查清單的哪一項，本章〈[Go 程式碼的 review 檢查清單](02_go_review_checklist.md)〉談過；意見怎麼寫、怎麼標輕重，本章〈[怎麼寫 review 意見](04_writing_review_comments.md)〉談過。這一集只談每一則該不該擋。

## 兩種極端

**什麼都擋。** 假設本章〈[先看設計，再看細節](01_design_before_details.md)〉列出的那些命名、註解與格式意見，每一則都標成「必須修改」：`ErrFull` 的訊息要不要縮短、`NewStore` 的參數叫 `n` 還是 `notifier`、測試名稱用哪一種格式。作者每改完一輪，reviewer 又看出新的偏好，PR 卡好幾天。真正的問題混在一堆「必須」裡，作者分不出哪些非改不可；下一次 reviewer 寫「必須修改」，作者也不會當真。

**什麼都放。** reviewer 看到 PR 只留一句 `LGTM`，沒有看。`before/` 原樣合併：額滿報名回 `nil`、持鎖通知、同一個人重複排進候補。這些問題 `after/` 各有一個測試，放到 `before/` 全部失敗，核准卻讓它們進了主幹。核准是 reviewer 說「看過了，同意」，沒看就按下去，PR 等於沒被 review，作者與維護者卻以為有。

兩種極端都沒有標準，結論看 reviewer 當天的心情，只是方向相反。

## 判斷的標準

每則意見依序問三個問題：

1. 合併之後，會不會有人得到錯的結果、被卡住、被攻擊？正確性、並行、安全的問題，會，就擋。
2. 這個決定合併之後，能不能便宜地收回？公開 API、錯誤契約、資料格式，一旦有呼叫端依賴就難以回頭，要特別嚴格：擋，或先拿到證據再放行（見下面〈難以回頭的變更要特別嚴格〉）。
3. 都不是，風險低、之後改的成本也低：核准並附意見，要改的事開 issue；純個人偏好（nit）不擋，作者採不採用都可以。

擋的意見要附證據：測試、可重現的步驟，或一個具體的情境。「覺得這樣不安全」不是理由，「放到 `before/` 會失敗的測試」是。放行也要說理由：風險在哪裡，為什麼低。

## 逐則判斷

| 意見 | 問題 | 結論 | 理由 |
| --- | --- | --- | --- |
| R1 設計 | 遞補寫在 handler | 擋 | 其他取消路徑漏掉遞補；測試證明 domain 的取消不遞補 |
| R2 錯誤契約 | 額滿時回傳 `nil` | 擋 | 呼叫端分不出成功與候補；難以回頭 |
| R3 並行 | 持有鎖時呼叫通知 | 擋 | 通知一慢，所有報名與取消都被卡住 |
| R4 正確性 | 候補者重複排入 | 擋 | 資料是錯的：同一個人排了兩次 |
| R5 API | 匯出的可變套件變數 | 要改，可以放行 | 新增的 API，還沒有人依賴 |
| R6 測試 | 缺候補者本人取消的測試 | 放行，開 issue | 實作是對的，缺的是覆蓋 |
| R7 nit | `cf`、`wl`、`nx` 的命名 | 不擋 | 個人偏好，風險低 |

R1～R4 各有一個 `after/` 的測試，放到 `before/` 都會失敗，所以這個 PR 的結論是要求修改；R5～R7 單獨看，一則都不會擋住合併。

R6 之所以不擋，是證據不同：R4 的測試放到 `before/` 會失敗，R6 的測試放到 `before/` 會通過。取消候補者本人的那條路徑，`before/` 的 `Cancel` 本來就是對的，缺的只是測試。R7 更輕，而且 R1 修好之後，`PromoteNext` 整個消失，那三個變數也就沒有了。

## 放行之後：開 issue，不要口頭承諾

「之後再補」沒有寫下來，就是不會補。核准並附意見時，合併前把後續事項開成 issue，並在 PR 留言連過去。`after/` 已經補了 R6 的測試；假設作者想讓 PR 先合併，issue 會長這樣：

```text
標題：補測試：取消的是候補者本人
來源：候補名單 PR 的 review 意見 R6
問題：Event.Cancel 取消候補者本人時，只該把他從候補名單移除，不遞補、不通知。
      目前的實作是對的，但沒有測試鎖住。
完成條件：外部測試套件新增一個測試，檢查 Confirmed()、Waitlisted()、Notified()。
風險：低。之後改動 Cancel 的人可能讓候補者本人的取消也觸發遞補，而測試不會失敗。
負責人：作者
```

issue 寫成別人看了就能做的樣子，有完成條件與負責人；「review 提過的那個」不算。要補的測試就是 `after/` 的這一個（用到的 `newEvent`、`join`、`fakeNotifier`，本章〈[先看設計，再看細節](01_design_before_details.md)〉列過）：

## 難以回頭的變更要特別嚴格

合併之後能不能收回，看的不是行數，而是有多少看不到的呼叫端。

- **R2。** 額滿時回傳 `nil`，HTTP 端點對應的是 201。一旦有呼叫端把「沒有錯誤」當成報名成功，合併後才改成回傳 `ErrWaitlisted`、202，這些呼叫端就會把候補誤當成失敗；錯誤契約的改動連編譯錯誤都沒有，第 2 章〈[錯誤是 API 契約的一部分](../chapter2/07_error_contract.md)〉談過。所以 R2 要在合併前擋。
- **改名。** 這個 PR 還把匯出方法 `Capacity()` 改成 `Seats()`、`Attendees()` 改成 `Confirmed()`，舊名稱消失，套件外的呼叫端編譯就失敗。這件事沒有 R 編號，也不能直接放行：先問有沒有 `signup` 以外的呼叫端。沒有就核准並附意見；有，就要求保留舊方法並標上 `// Deprecated:`（第 1 章〈[棄用（deprecation）與相容性](../chapter1/08_deprecation_and_compatibility.md)〉談過），或確認呼叫端同步改完再合併。改名單獨成一個 PR，這個問題才不會埋在功能裡，本章〈[PR 大小與拆分](03_pr_size_and_split.md)〉談過拆分。
- **資料格式。** 改名沒有動 JSON 的 `capacity` 與 `attendees`，線上格式不變，這是對的。客戶端不會跟著重新編譯，資料格式比 Go 識別字更難收回。

同樣是公開 API，R5 可以放行、改名要先問：R5 是新增的名稱，沒有人依賴；改名是拿掉已經有人呼叫的方法。

## 意見不一致時怎麼收斂

reviewer 與作者，或兩位 reviewer 意見不同時：

- 回到標準，不比資歷。這則意見落在三個問題的哪一個？要擋的得有證據；落在 nit 的，由作者決定。
- 看團隊的慣例與文件。有寫下來的規則就照它；沒有，就把這次的結論寫進文件，下次不必再爭。這類決定怎麼留下紀錄，第 14 章〈[設計文件與 ADR 的關係](../chapter14/06_design_doc_and_adr.md)〉談過。
- 來回幾輪還沒收斂，改成面對面或同步討論（本章〈[怎麼寫 review 意見](04_writing_review_comments.md)〉談過時機），結論回貼到 PR；仍然僵持，交給維護者決定，並記下理由。

## 取捨

- 三個問題不是公式。R3 的通知若永遠不會慢，擋不擋？`Notifier` 是呼叫端提供的介面，今天的實作快，不代表之後的實作不會去呼叫外部服務，所以仍然擋（持鎖時呼叫外部程式碼的問題，第 6 章〈[channel 與 mutex 怎麼選](../chapter6/07_channel_or_mutex.md)〉談過）；這類判斷靠的是對情境的理解，標準只負責讓判斷說得出理由。
- 擋有代價：作者多改一輪，PR 多等一輪。事故中趕著止血的 PR，標準會調整：先放行，缺的補在後續並開 issue，第 15 章〈[先止血，再找原因](../chapter15/02_mitigate_first.md)〉談過。調整的是時機，擋的理由沒有消失。
- 放行也有代價：issue 沒人處理，就變成永遠的技術債；放行太多，等於標準悄悄降低。放行不是保證沒有問題，是依目前的證據，風險可以接受。
- 什麼都擋在有些地方是對的：安全修正、金流、資料遷移，一點風險都不能留，標準本來就更嚴。什麼都放則適合不會上線的原型與一次性腳本。
- 內部套件、所有呼叫端都在同一個 repo 時，不必對公開 API 過度保守；對外發布的函式庫，R5 同樣的問題就要擋。

## 重點整理

- 擋與放行要有標準：合併後會不會出錯、卡住、被攻擊；能不能便宜地收回；其餘核准並附意見，nit 不擋。
- 擋的意見附證據（R1～R4 各有放到 `before/` 會失敗的測試）；放行要說風險為什麼低（R6 的測試放到 `before/` 會通過，缺的是覆蓋，不是 bug）。
- 放行時把後續事項開成 issue，寫清楚完成條件與負責人；口頭承諾等於不會做。
- 公開 API、錯誤契約、資料格式難以回頭，要特別嚴格：先問有沒有看不到的呼叫端。
- 意見不一致時回到標準與團隊文件，不比資歷；兩個極端的共通點是沒有標準。
