# 怎麼寫 review 意見

## 本集目標

同一個問題，意見可以寫得讓作者猜，也可以寫得讓作者一看就動手：說出問題與後果、給出建議或問題、標明輕重。這一集學的是怎麼寫成後者。

## 情境

還是那個「加入候補名單」PR。本集拿三個問題各寫兩個版本，含糊的與具體的：額滿時報名回傳 `nil`（R2）、持有鎖時呼叫通知（R3）、區域變數的縮寫看不出意思（R7）。R7 的含糊版就是本章〈[先看設計，再看細節](01_design_before_details.md)〉列過的那一則；R2、R3 的含糊版是常見的寫法，不是那個 PR 實際收到的意見。怎麼找出這些問題是本章〈[Go 程式碼的 review 檢查清單](02_go_review_checklist.md)〉的事，本集只談找到之後怎麼寫。

意見是寫在 PR 對應那一行旁邊的文字，作者與 reviewer 往往不在同一時間讀，作者不能當面問「這句是什麼意思」。三則意見指的程式碼是：


```go,ignore

```

`Register` 把人排進候補時 `return nil`（R2）；它用到的 `normalize` 與 `MaxWaitlist`，本章〈[Go 程式碼的 review 檢查清單](02_go_review_checklist.md)〉交代過。`PromoteNext` 持有鎖直到函式結束（`defer e.mu.Unlock()`），`Notify` 就在這段時間裡呼叫（R3），區域變數叫 `cf`、`wl`、`nx`（R7）。

## 含糊的意見讓作者猜

```text
event.go      Register：這樣不好。
waitlist.go   Notify 那一行：為什麼不用 goroutine 通知？
waitlist.go   PromoteNext 裡的 cf、wl、nx 看不出是什麼意思，請改名。
```

作者收到這三則，得猜三件事：

- **問題是什麼。** 「這樣不好」指的是回傳 `nil`、排進候補的做法、`MaxWaitlist`，還是鎖？
- **要做什麼。** 「為什麼不用 goroutine 通知？」是提問還是要求？照字面改成 `go e.notifier.Notify(nx)`，鎖是放開了，但這個 goroutine 沒有人負責等它結束，第 6 章〈[goroutine 的生命週期歸誰管](../chapter6/01_goroutine_ownership.md)〉談過。`cf`、`wl`、`nx` 要改成什麼，也只能自己想。
- **多重要。** 三則的口氣一樣平，作者分不出哪一則一定要處理、哪一則改不改都可以。

猜錯的成本雙方都要付：作者改錯方向，reviewer 再讀一輪、再寫一輪。

## 具體、可行動、標明輕重

一則意見寫四件事：

1. **問題**：哪個函式、發生了什麼事，寫程式碼裡看得到的事實。
2. **後果**：不處理會怎樣、誰會碰到。
3. **建議或提問**：建議的做法；沒把握的地方寫成問題，不要把猜測寫成斷言。
4. **輕重**：標籤放在最前面，作者先知道這則要花多少力氣。

本章用四個標籤：

| 標籤 | reviewer 的期待 |
| --- | --- |
| 必須修改 | 這是問題，作者要處理：改程式碼，或說明為什麼不是問題 |
| 建議 | 改了會更好；作者可以不改，但要回一句理由 |
| nit | 小細節；想改就改，不改也不必回覆 |
| 提問 | reviewer 不確定，不是要求；作者回答，答案可能讓這則撤回，或改標成別的標籤 |

標籤說的是這則意見的輕重，不是 PR 通過與否的決定；哪些問題值得讓 PR 停下來，本章〈什麼時候該擋、什麼時候可以放行〉會談。標籤的定義各團隊不一，重點是同一個團隊用同一套。

## R2、R3、R7 的前後對照

R2：

> R2 必須修改：`Register` 在名額已滿、把人排進候補名單時回傳 `nil`，和報名成功一模一樣。呼叫端分不出兩種結果，handler 會對候補的人回 201，使用者以為拿到名額。建議讓兩種結果分得出來，例如回傳可以用 `errors.Is` 判斷的錯誤值，或改成回傳一個結果型別；兩種都可以，請在 PR 說明選哪一種、為什麼。

回傳值是函式對呼叫端的承諾，第 2 章〈[錯誤是 API 契約的一部分](../chapter2/07_error_contract.md)〉談過。這則意見把問題、後果與兩個方向都寫了，選擇留給作者。

R3：

> R3 必須修改：`PromoteNext` 持有 `e.mu` 時呼叫 `Notify`。通知服務一慢，這場活動的報名、取消與查詢都卡在同一把鎖上。建議在鎖內只決定要通知誰，解鎖之後才呼叫 `Notify`。另外請補一個測試：通知卡住時，另一個報名仍然要完成。

不在鎖裡呼叫會阻塞的函式，第 6 章〈[channel 與 mutex 怎麼選](../chapter6/07_channel_or_mutex.md)〉談過。這則意見給的是一個方向加一個驗證的方式，不是整段程式碼。

R7：

> R7 nit：`PromoteNext` 裡的 `cf`、`wl`、`nx` 看不出是什麼，建議寫成 `confirmed`、`waitlist`、`next`。不影響行為，改不改都可以。

和含糊版相比，多的只有標籤與建議的名字，作者就知道這則不必花力氣爭論。

## 語氣：談程式碼，不談人

- 意見的主詞是程式碼，不是作者。「你怎麼會把通知放進鎖裡？」評斷的是人；「`PromoteNext` 持有鎖時呼叫 `Notify`」描述的是程式碼，作者也比較好回應。
- 不用反問與諷刺（「這是認真的嗎？」）。真的想知道，就用「提問」標籤，認真問。
- 值得稱讚的地方也寫，而且寫具體，作者才知道哪個做法要保持：

> `Notifier` 由呼叫端提供，測試用假的實作，不必起真的通知服務就能測遞補。

讚美不必標輕重，也不必當成批評前的墊檔；沒有值得寫的就不寫。

## 什麼時候改用同步討論，怎麼收斂

文字意見來回兩輪還沒有共識，就約時間當面或通話談，不要寫第三輪。適合同步談的情況：分歧在方向而不在細節（整個 PR 的做法要不要換）；一則意見牽涉好幾個檔案，文字說不清楚；回覆讀起來帶火氣，或意見可能被讀成針對個人。設計層級的討論該寫在設計文件裡，PR 不是討論設計的地方，第 14 章〈[什麼時候需要寫](../chapter14/01_when_to_write.md)〉談過。

談完回 PR 寫一則摘要：結論與理由。決定只留在通話裡，之後讀這個 PR 的人看不到為什麼這樣改。

作者那一側，每則意見都要有一個結果，reviewer 才不必猜：已改（說明怎麼改）、不改（說明理由）、已回答（對提問）。以 R2、R3、R7 為例：

```text
R2  已改：額滿排進候補時回傳 ErrWaitlisted，呼叫端用 errors.Is 判斷；handler 回 202。
R3  已改：鎖內只決定誰遞補，解鎖後才 Notify；補了測試：通知卡住時，另一個報名仍然完成。
R7  已改：遞補的邏輯搬進 remove（隨 R1 的修改），變數改叫 next 與 promoted。
```

R2 選錯誤值而不是結果型別的理由，寫在 `ErrWaitlisted` 的文件註解裡，也是一種回覆：

```go,ignore
{{#include ../../../examples/chapter13/01_design_before_details/after/errors.go:waitlisted}}
```

reviewer 確認修改符合意見之後，才把那則討論標成已解決；誰來關，團隊先約好，不要各關各的。

## 取捨

- 四個部分寫齊要花時間。小 PR、彼此熟悉的同事之間，「nit：`cf` 改成 `confirmed`」一行就夠；後果與建議留給必須修改的那幾則。
- 標籤要團隊先約好。沒有共識的話，reviewer 寫的「建議」會被當成「必須修改」，nit 則被當成可以不看。
- 建議只給方向，不給整段程式碼：作者可能有更好的做法（R2 就留了兩個選項）。reviewer 直接代寫，等於把設計換成自己的。
- 同步討論快，但留不下紀錄，所以才要補摘要。作者與 reviewer 在不同時區、不同班表時，文字意見寫得夠具體，就是唯一的溝通方式。
- 一次留二十則 nit，會蓋過那一則真正重要的。nit 多的時候合併成一則，或另外挑時間處理。

## 重點整理

- 含糊的意見讓作者猜三件事：問題是什麼、要做什麼、多重要。
- 一則好意見有問題、後果、建議或提問、輕重四個部分；輕重用標籤寫在最前面：必須修改、建議、nit、提問。
- 標籤說的是意見的輕重，不是 PR 通過與否的決定，後者是本章〈什麼時候該擋、什麼時候可以放行〉的事。
- 意見的主詞是程式碼，不是人；值得稱讚的地方寫具體。
- 來回兩輪還沒共識就改用同步討論，並把結論寫回 PR；每則意見都要有已改、不改或已回答的結果。
