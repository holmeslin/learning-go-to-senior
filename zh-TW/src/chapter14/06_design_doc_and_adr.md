# 設計文件與 ADR 的關係

## 本集目標

判斷決定做完之後，該留在設計文件裡，還是另外記成 ADR（architecture decision record，架構決策紀錄）：設計文件是討論的過程，寫完就不再更新；ADR 是決定的紀錄，短、放在 repo、內容不改；決定要變時，新增一則取代舊的。

## 情境

假設活動提醒通知照設計文件做完、上線了，選定的是方案 A：定期掃描資料庫的 worker。完整的設計文件在本章〈[結構：背景、目標、非目標、方案、取捨](02_doc_structure.md)〉。日後某一天，新來的維護者讀到掃描的程式碼，覺得訊息佇列的延遲工作（方案 B）也許更好，打開設計文件，想弄清楚當初為什麼不用。

決定怎麼走到結論，本章〈[替代方案怎麼寫](04_alternatives.md)〉與〈[設計文件的 review](05_design_review.md)〉談過。這集談的是決定做完之後，文件的下場。

## 決定埋在設計文件裡

文件找得到，B 為什麼不選也寫在裡面，維護者卻得在一份很長的文件裡翻找，才拼得出答案：

- 替代方案、取捨、review 的留言與回應散在不同段落，讀的人不知道哪一段才是決定。結論只是「取捨」段開頭的一句「選方案 A，換來的是……」。
- 理由混在方案的比較與 review 的留言串裡，和當時的限制（維運只有一個人、不想新增基礎設施）攪在一起。哪些是決定性的，哪些只是順帶一提，讀的人得自己猜。
- 「先跑在報名服務的行程內，之後再拆」這個有風險的取捨，夾在未決問題與討論串之間。

文件還有可能根本找不到：文件工具搬過一次資料夾，連結失效，當初的作者也轉了組。於是同一場爭論重來一遍：B 要不要新增佇列？取消報名時已排入的工作怎麼撤回？花同樣的時間，結論未必和當初一樣，因為當時的限制沒有人記得。更糟的是沒找到就直接改，做到一半才撞上 B 當初被淘汰的理由。

## 從設計文件抽出一則 ADR

ADR 只記一個決定，分四個部分：背景（當時的限制）、決定、後果（接受了什麼代價）、狀態。內容從設計文件摘出來，不重寫討論：

```markdown
# ADR-0012：提醒通知用定期掃描資料庫的 worker

狀態：已接受（2030-03-04）
設計文件：活動提醒通知（連結）

## 背景

活動開始前 24 小時，要對每位報名成功的人寄一次提醒（email 與推播），並在預定時間後 1 小時內寄出。推播供應商限制每秒 50 次，email 供應商有每日額度，熱門活動一場最多約 2 萬名報名者。維運只有一個人，不想新增需要維運的基礎設施。

## 決定

在報名服務裡加一個 worker，每 5 分鐘掃描資料庫，找出 24 小時內開始、還沒有提醒紀錄的報名。寄出之前先寫一筆以「活動 + 報名者」為冪等鍵的紀錄，靠資料庫的唯一限制擋掉重複，寫得進去的才限流送出；失敗重試，預定時間後 1 小時仍失敗就放棄，記成失敗數。寧可不寄，也不重複。worker 先跑在報名服務的行程內，之後再拆。用設定開關控制是否啟動，先在一部分活動啟用。

不採用的方案：B（報名時排入訊息佇列的延遲工作）要新增並維運訊息佇列，取消報名時還要撤回已排入的工作；C（行程內的計時器）在行程重啟時遺失，多個副本會重複寄送。

## 後果

- 不新增基礎設施，資料庫是唯一的事實來源，重啟後下一輪接著掃。
- 提醒最多晚 5 分鐘寄出，資料庫多一個定期查詢。
- 寫完紀錄、寄出之前中斷的那一筆不會補寄：接受漏寄，換來不重複。
- worker 與報名服務共用行程與部署：worker 出問題會影響報名服務。設定開關可以先把 worker 關掉。
```

編號與日期都是虛構的範例。每個部分只摘「一年後有人問為什麼」會用到的東西：目標與非目標的完整清單、上線計畫留在設計文件；方案的比較也不搬過來，ADR 只要讓人知道選項存在過、淘汰的理由是什麼。後果要寫代價，最後一條是風險，不是好處：日後讀到的人看得出這是當時接受過的取捨，不是疏忽。這個取捨之後的發展，第 15 章〈[事後檢討（blameless postmortem）](../chapter15/04_blameless_postmortem.md)〉談過。設計文件的連結只當延伸閱讀，連結失效時，ADR 本身仍要讀得懂。

## 改變決定：新增一則，不改舊的

下面是示範用的假設，不是這份設計實際的發展：假設日後平台為了別的功能，已經在維運一套訊息佇列，維護者想改用方案 B。這時不去改 ADR-0012，新增一則：

```markdown
# ADR-0031：提醒通知改用訊息佇列的延遲工作

狀態：已接受（2031-05-20）
取代：ADR-0012

## 背景

ADR-0012 淘汰方案 B 的理由是要新增並維運訊息佇列。平台現在已經為別的功能維運一套，這個理由不再成立；掃描的 5 分鐘延遲與資料庫的定期查詢仍在。

## 決定

報名時把提醒排入佇列的延遲工作，時間到由消費者寄出；取消報名時撤回已排入的工作。遷移期間新舊兩套並存，以同一個冪等鍵避免重複寄送，完成後移除 worker。

## 後果

- 提醒不再受掃描週期影響，資料庫少一個定期查詢。
- 取消報名要撤回已排入的工作，這是 ADR-0012 當時挑出的方案 B 的代價，現在由報名服務承擔。
- 提醒的事實來源從資料庫變成資料庫加佇列，兩者要保持一致。
```

ADR 的規矩是內文不改，只把狀態改成已取代。ADR-0012 的內文一個字都不動，只改狀態那一行，指向新的那一則：

```diff
-狀態：已接受（2030-03-04）
+狀態：已被 ADR-0031 取代（2031-05-20）
```

ADR-0012 記的是在當時的限制下，A 是合理的選擇。若直接改寫成「改用 B」，這段歷史就消失了，下一個讀者分不出 A 是判斷錯誤，還是條件變了。有了取代的關係，兩件事都留得下來：ADR-0031 的背景指出哪一個條件變了。狀態常見的值有四個：提議中（PR 還沒合併）、已接受、已被某則取代、已廢棄（決定不再適用，也沒有新的決定接手）。

## 分工，以及放在哪裡

| | 設計文件 | ADR |
| --- | --- | --- |
| 回答 | 要怎麼做、有哪些選項 | 當初決定了什麼、為什麼 |
| 讀者 | reviewer，決定之前評估 | 未來的維護者，決定之後查閱 |
| 長度 | 可以很長，含替代方案與討論 | 一頁以內，只有一個決定 |
| 完成後 | 不再更新，停在宣告決定的那個版本 | 內容不改，只改狀態 |
| 放哪裡 | 文件工具，需要留言討論 | repo，跟程式碼一起 |
| 數量 | 一個功能一份 | 一個決定一則，一份文件可以抽出好幾則 |

設計文件不再更新，連開頭的狀態也不補：它停在本章〈[設計文件的 review](05_design_review.md)〉宣告決定的那一刻，「狀態：已決定」與日期說明這是當時的版本，現況看 ADR。決定之後若被取代，變的只有 ADR 的狀態。

ADR 放在報名服務的 repo，例如 `docs/adr/0012-reminder-db-scan-worker.md`（虛構的路徑，指的是報名服務的 repo，不是本書的 repo）：

- 跟著程式碼走：切到舊版就看得到當時的 ADR，新增或改狀態也經過 PR review，`git log` 查得到是哪一次改的。
- 不依賴文件工具的帳號、權限與網址。
- 編號只增不減、不重用，檔名帶編號與短標題，目錄列表就是決定的時間線。

review 意見有分歧時，團隊寫下來的決定就是依據；第 13 章〈[什麼時候該擋、什麼時候可以放行](../chapter13/06_block_or_approve.md)〉談過要先看團隊的慣例與文件，ADR 是這類決定的家。

哪些決定值得寫？判斷依據和本章〈[什麼時候需要寫](01_when_to_write.md)〉相同：難以回頭、有多個合理做法、接受了明顯的代價、影響別的團隊或日後寫程式的方式。ADR 的門檻更低，因為它短。一個簡單的判斷：一年後有人問「為什麼這樣」，答案不在程式碼裡，一句 commit 訊息也講不完，就寫。ADR 不需要先有設計文件，review 時臨時改變的做法，也可以只留一則 ADR。命名或隨手能改回去的實作細節不用寫。

## 取捨

- ADR 也有成本：要寫、要 review。小決定都寫，真正重要的反而被淹沒；寫成設計文件的縮小版，更沒有人讀。
- 不改舊的，讀者就得沿著取代的關係找到最新的決定。狀態那一行與依編號排列的目錄，是唯一的索引。有些團隊連狀態行都不動，只靠新 ADR 的「取代」欄位反查；代價是從程式碼註解點進舊 ADR 的人，看不出它已經過期。
- 設計文件不再更新，會與現況慢慢脫節；宣告決定時寫下的狀態與日期要寫清楚，讀的人才看得出這是當時的版本，現況看 ADR。
- 只留設計文件在有些地方是對的：文件本身就一頁、放在 repo 裡、決定很少改的小專案，文件就是紀錄。
- ADR 寫得不誠實，只有好處、沒有代價，就沒有價值。後果段要寫出日後會被問到的那一條，例如這一則的「worker 與報名服務共用行程」。

## 重點整理

- 決定埋在長長的設計文件裡，一年後很難找到理由、也看不出哪一段才是決定，只好重新爭論；ADR 把決定與理由單獨留下來。
- ADR 一則一個決定，四個部分：背景、決定、後果、狀態；後果要寫代價，包括 worker 與報名服務共用行程的風險。
- 設計文件是討論的過程，可以很長，完成後不再更新；ADR 短，放在 repo，跟程式碼一起 review。
- 決定要變時新增一則 ADR 取代舊的；舊的內文不改，只把狀態改成已被新的那一則取代。
- 難以回頭、有多個合理做法、接受了明顯代價的決定，才值得寫成 ADR；隨手能改回去的細節不用。
