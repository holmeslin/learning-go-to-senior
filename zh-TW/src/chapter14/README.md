# 設計文件

有些決定不該等到 PR 才討論：程式碼寫完了才發現方向錯，代價是整個 PR。跨好幾個套件或服務、要做好幾週的功能，常見的狀況是：該寫設計文件的大改動直接開工，做到一半才發現另一個團隊的假設不同；不需要的小改動卻被要求寫長文件；文件寫成實作細節的流水帳，沒寫目標與非目標，讀的人不知道要評估什麼；同一份文件想同時寫給主管、reviewer 和未來的維護者，結果誰都看不懂；替代方案只是湊數；設計 review 變成挑字眼，或沒人看就核准；決定做完之後只留在一份很長的文件裡，一年後沒人找得到「當初為什麼這樣選」。

這一章的主題是在寫程式之前，把需要大家同意的決定寫下來並取得同意。全章用同一份設計文件當例子：虛構的「活動報名平台」要加上「活動提醒通知」，作者寫文件、送給不同的讀者、列出替代方案、經過設計 review，最後把關鍵決定記成 ADR（architecture decision record）。設計文件與 ADR 的片段都寫在頁面上，這一章沒有要執行的程式碼。平台、團隊與數字都是虛構的教材範例，文中的人一律用角色稱呼。
