# 什麼時候需要寫

## 本集目標

面對一個要動手的改動，依四個問題判斷要不要先寫設計文件：改完難不難回頭、牽不牽涉別的團隊、要不要做好幾週、有沒有多個合理做法要選。只符合一兩項的，寫一頁就夠；一項都不符合，直接做。

## 情境

虛構的活動報名平台上，報名後沒有出席的比例偏高。產品負責人希望在活動開始前提醒報名者，這就是「活動提醒通知」。報名服務已經在跑（第 13 章的候補名單就是它的一部分），資料在關聯式資料庫，維運只有一個人。

同一週，作者手上還有幾件小事：改一個錯字、把重複的程式碼抽成函式。團隊對「哪些改動要先寫設計文件」沒有共識，這一集談的就是這條線。文件裡每一段要寫什麼，本章〈結構：背景、目標、非目標、方案、取捨〉會談。

## 兩種錯誤

**該寫沒寫。** 作者拿到提醒通知，覺得需求很清楚：活動開始前 24 小時，對每位報名成功的人寄一次 email 與推播。於是直接開工，在報名服務裡寫一段程式，到時間就把所有報名者一次送出，用幾個測試帳號測試，全部通過。

做到一半才發現兩件事。第一，熱門活動一場最多約 2 萬名報名者，推播供應商限制每秒 50 次，一次全送會撞上限流；改成排隊慢慢送，光推播 2 萬人就要 400 秒，約 7 分鐘，這個數字會左右後面的設計。第二，推播供應商的串接由另一個團隊（行動 App 團隊）維護，目前只用在 App 的其他通知；他們原本以為提醒會在報名成功後逐筆送出，沒有人想過活動前一次要送兩萬筆。

這時候程式已經寫了大半，方向卻要改：丟掉重寫，或硬改，或等到 PR 才被 reviewer 指出來。第 13 章〈[先看設計，再看細節](../chapter13/01_design_before_details.md)〉談過，PR 才看出方向不對，成本已經付了。這兩件事在動手之前，花半天算一下數字、問行動 App 團隊一句話，就能發現。

**不該寫卻寫。** 同一週，作者發現錯誤訊息裡有個錯字，reviewer 要求「改動要先寫設計文件」。作者為一個字寫了背景、方案與風險，等 review 的時間比改動本身還長，改動只有一行。更糟的是之後：大家學到文件是過關的形式，隨便寫、隨便核准，等到真正需要的時候，文件已經沒有人認真讀了。

## 判斷的依據

四個問題，每個問題都是在問「走錯的時候，代價有多大」：

1. **難以回頭嗎？** 資料格式、公開 API、跨服務的契約，一旦有資料或呼叫端依賴就收不回。公開 API 的部分，第 1 章〈[匯出名稱與 API 穩定性](../chapter1/04_exported_api_stability.md)〉談過：匯出之後，名稱就是對呼叫端的承諾；第 13 章〈[什麼時候該擋、什麼時候可以放行](../chapter13/06_block_or_approve.md)〉談過，看的不是行數，而是有多少看不到的呼叫端。資料格式的部分，第 4 章〈[migration](../chapter4/06_migration.md)〉談過 schema 怎麼先擴充、再收斂，讓還在跑的舊版不壞。
2. **牽涉多個團隊嗎？** 另一個團隊的假設，只有問了才知道；寫成文件，對方才有機會在動手之前說「推播不是這樣用的」。
3. **要做好幾週嗎？** 三天的工作走錯了，重來的代價還能接受；做了好幾週才發現，代價就是好幾週。
4. **有多個合理做法要選嗎？** 只有一種做法，沒什麼好同意的；有好幾種，而且各自的代價不同，選擇本身就需要被同意。

把提醒通知和幾個小改動放進這四個問題：

| 改動 | 難以回頭 | 多個團隊 | 好幾週 | 多個合理做法 | 結論 |
| --- | --- | --- | --- | --- | --- |
| 修錯誤訊息的錯字 | 否 | 否 | 否 | 否 | 直接做 |
| 把 handler 裡重複的程式碼抽成函式 | 否 | 否 | 否 | 有，但改起來便宜 | 直接做 |
| 報名 API 回應裡的日期欄位，改成另一種格式 | 是，有客戶端依賴就收不回 | 是，另一個團隊的客戶端會讀 | 否 | 否 | 寫一頁 |
| 活動提醒通知 | 是，跨服務的契約，寄出的通知也收不回 | 是，推播的串接在行動 App 團隊 | 是 | 是，至少三種做法 | 寫完整的設計文件 |

一項都不符合，直接做，但 PR 描述要把「要解決什麼問題、不做什麼」寫清楚，這是第 13 章〈[先看設計，再看細節](../chapter13/01_design_before_details.md)〉列的 review 第一步。符合一兩項，寫一頁。四項都符合，就是提醒通知這種要寫完整的。「至少三種做法」各自怎麼比，本章〈替代方案怎麼寫〉會談。

## 寫的成本，與一頁的版本

文件的成本不只是打字。作者要花時間寫，reviewer 要花時間讀，作者還得等 review 回來才能放心動手，這段等待對小改動不值得。好處也在寫的過程：上面那個 400 秒的算術，是作者被迫寫下「每場活動最多多少人、供應商每秒能收多少」才會做的事。

要寫，也不必一開始就寫完整。一頁的版本，一個畫面讀得完：

```markdown
## 要解決什麼問題
一兩句：誰遇到、現在怎麼樣。

## 要做什麼、不做什麼
各三條以內；不做的也要寫出來。

## 選的做法，與放棄的一個做法
各一段，說明為什麼。

## 需要誰同意
點名角色，例如另一個團隊的維護者。
```

日期欄位那個改動，一頁就夠：重點是讓另一個團隊在動手之前，有機會說「客戶端沒辦法這樣改」。

## 先做 prototype 的情況

有些不確定，寫文件回答不了。分兩種：

- **不確定的是做不做得到。** 例如推播供應商超過每秒 50 次時，到底是拒絕、排隊還是丟棄，說明文件沒講清楚。寫一支用完就丟的小程式，對供應商發幾個請求看回應，比開會討論快。
- **不確定的是該選哪個。** 提醒通知有好幾種做法，各有各的取捨，prototype 回答不了，只會做出幾個半成品。這要先寫下來，讓大家同意。

prototype 只回答一個問題，事先講好做多久；做完丟掉，不直接合併，否則又回到「都做完了，先放行吧」，第 13 章〈[先看設計，再看細節](../chapter13/01_design_before_details.md)〉的取捨談過這種壓力；結論回寫到文件裡，讓 reviewer 看得到文件的依據是什麼。

## 取捨

- 四個問題不是公式。邊界上的改動，靠的是對情境的理解；問題的用處是讓判斷說得出理由。作者自己先判斷，拿不準就問 reviewer 或維護者，一句話就夠。
- 寫有代價，不寫也有。一個人、一個服務、三天做完、隨時改得回來的改動，PR 描述就夠；反過來，一頁文件放在小改動上，也可能是多餘的。
- 「一律要寫」的規則，最後多半走向第二種錯誤，文件變成形式；「靠默契」則走向第一種。兩種都是因為沒有標準，只是方向相反。
- 文件擋不住所有問題。寫了，也可能漏掉限制；它的價值是讓假設攤開被看見。怎麼看，本章〈設計文件的 review〉會談。

## 重點整理

- 該不該先寫，看走錯的代價：難以回頭、牽涉多個團隊、要做好幾週、有多個合理做法要選。
- 兩種錯誤都有成本：該寫沒寫，代價是整個 PR；不該寫卻寫，代價是等待，以及文件變成形式。
- 一項都不符合就直接做，PR 描述寫清楚；符合一兩項寫一頁；多項都符合才寫完整。
- 一頁版本只有四件事：問題、做什麼與不做什麼、選的與放棄的做法、需要誰同意。
- 不確定做不做得到，先做用完即丟的 prototype；不確定該選哪個，先寫下來讓大家同意。
