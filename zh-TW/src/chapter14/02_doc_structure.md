# 結構：背景、目標、非目標、方案、取捨

## 本集目標

動手寫設計文件時，知道每一段要回答什麼問題：背景說明為什麼現在做，目標要能檢驗，非目標擋住範圍蔓延，方案與取捨寫到讀的人能評估；並判斷哪些細節留在程式碼，不放進文件。

## 情境

虛構的活動報名平台上，產品負責人希望活動前提醒報名者，降低報名了卻沒出席的比例。這個改動牽涉資料庫與兩家外部供應商，要做好幾週，值得先寫設計文件（什麼時候需要寫，本章〈[什麼時候需要寫](01_when_to_write.md)〉談過）。

作者打開空白文件，第一個念頭常是從實作寫起：資料表長什麼樣、worker 的函式叫什麼名字。讀的人要評估的卻是別的：這個改動值不值得做、做完怎麼算成功、為什麼選這個做法。

本章全章用這一份「活動提醒通知」文件當例子；這集給出它的完整樣子（已精簡），再說明每一段為什麼存在。

## 骨架：每一段回答一個問題

| 段落 | 要回答的問題 |
| --- | --- |
| 背景 | 為什麼是現在？不做會怎樣？有哪些限制？ |
| 目標 | 做完怎麼知道成功？ |
| 非目標 | 哪些相關的事這次不做？ |
| 方案 | 打算怎麼做？ |
| 替代方案 | 還考慮過什麼，為什麼沒選？ |
| 取捨 | 選這個方案，要付出什麼代價？ |
| 風險 | 什麼可能出錯，影響多大？ |
| 上線與回復 | 怎麼分階段開？出事怎麼退？ |
| 未決問題 | 還有什麼沒決定，需要誰回答？ |

## 範例：活動提醒通知

下面是作者送去 review 的版本；review 之後怎麼改，本章〈設計文件的 review〉會談。

```markdown
# 活動提醒通知

狀態：待 review　reviewer：維護者、另一個團隊

## 背景

報名成功卻沒出席的比例偏高，產品負責人希望活動前提醒報名者。
報名服務已有報名資料，存在關聯式資料庫；目前沒有任何對報名者主動發訊息的機制。

已知限制：

- 推播供應商限制每秒 50 次；email 供應商有每日額度。
- 熱門活動一場最多約 2 萬名報名者。
- 團隊只有一個人維運，不想新增需要維運的基礎設施。

## 目標

- 活動開始前 24 小時，對每位報名成功的人寄一次提醒，管道是 email 與推播。
- 每位報名者每場活動最多收到一次提醒。
- 提醒在預定時間後 1 小時內寄出。
- 寄出數、失敗數、延遲可以觀測。

## 非目標

- 簡訊。
- 使用者自訂提醒時間，或關閉個別提醒。
- 行銷訊息。
- 候補者的提醒。

## 方案

新增一個 worker，每 5 分鐘掃描資料庫，找出「24 小時內開始、尚未寄提醒」的報名。
以「活動 + 報名者」當冪等鍵，記錄已寄出的提醒；送出前先限流，失敗就重試。

## 替代方案

- B：報名時排入延遲工作到訊息佇列，時間到由消費者寄出。不選：要新增並維運訊息佇列，取消報名時還要撤回已排入的工作。
- C：行程內的計時器，每場活動在報名服務裡開一個 timer。不選：行程重啟就遺失，多個副本會重複寄送。

## 取捨

選方案 A，換來的是：不新增基礎設施、資料庫是唯一的事實來源、重啟不會遺失。
要接受的缺點：掃描最多有 5 分鐘的延遲（目標允許 1 小時），資料庫多一個定期查詢。

## 風險

- worker 若跑在報名服務的行程內，它出問題會影響報名服務。
- 推播被限流或 email 額度用完，提醒會延後；延遲有觀測，超過 1 小時看得出來。
- 定期查詢增加資料庫的負擔；只查 24 小時內開始的活動。

## 上線與回復

用設定開關控制 worker 是否啟動，先在一部分活動啟用。出問題就關掉開關；已寄出的提醒收不回來。

## 未決問題

- worker 跑在報名服務的行程內，還是獨立部署？前者少一個要維運的部署單位，後者不會拖累報名。
```

## 每一段怎麼寫

**背景**要把限制寫進來，因為方案是被限制推出來的：推播每秒 50 次，所以方案要限流；只有一個人維運，所以不新增基礎設施。讀的人看到限制，才知道方案不是隨意挑的。

**目標**要能檢驗。含糊的目標，做完之後沒人說得出有沒有達成：

| 含糊 | 可檢驗 |
| --- | --- |
| 盡量不要重複寄 | 每位報名者每場活動最多收到一次 |
| 提醒要及時 | 預定時間後 1 小時內寄出 |
| 要能監控 | 寄出數、失敗數、延遲可以觀測 |

「1 小時內寄出」是第 9 章〈[SLI 與 SLO](../chapter9/08_sli_slo.md)〉談過的那種目標：延遲量得出來，才檢驗得了；第三條「可以觀測」就是在要求這個前提。

**非目標**寫「有人會合理地期待，但這次不做」的事，不寫「不可能發生」的事。review 時有人問「簡訊呢？」，作者指著非目標，討論就結束；沒有這一段，每個相關的需求都變成要回答的問題，範圍一路長大。非目標是「這次不做」，不是「不能做」。

**方案**寫需要別人同意的決定：掃描間隔、冪等鍵由什麼組成、有限流與重試。這些做法怎麼實作，前面的章節談過，文件不必重講：第 10 章〈[冪等性](../chapter10/03_idempotency.md)〉、〈[`golang.org/x/time/rate` 限流](../chapter10/04_rate_limit.md)〉、〈[重試、退避與 jitter](../chapter10/02_retry_backoff_jitter.md)〉。

**替代方案**這裡只寫兩行，怎麼比較才公平，本章〈替代方案怎麼寫〉會談。**取捨**要把缺點寫出來，並對照目標檢查：5 分鐘的延遲在「1 小時內」之內，所以接受。

**風險**寫「worker 出問題會影響報名服務」這個取捨的代價，不用先替它找藉口；真的出問題之後怎麼處理，第 15 章會談。**上線與回復**的開關，第 12 章〈[設定與環境變數](../chapter12/08_config_env.md)〉談過怎麼讀、怎麼驗證。**未決問題**不是缺陷，是作者明說「這裡還沒有定論」，reviewer 才知道該回答什麼。

## 文件放多少細節

判斷的問題：這個細節改了，需要讓 reviewer 重新同意嗎？

| 需要，屬於文件 | 不需要，留在程式碼與 PR |
| --- | --- |
| 掃描間隔 5 分鐘（影響「1 小時內」） | 資料表與欄位的名字、索引 |
| 冪等鍵由「活動 + 報名者」組成（決定「最多一次」） | 函式與型別怎麼切、log 的欄位 |
| worker 跑在哪個行程 | 查詢的逾時設在哪一層，第 4 章〈[查詢逾時該設在哪一層](../chapter4/03_query_timeout_layer.md)〉談過 |

上面的範例約一到兩頁。文件長到需要目錄時，先問是不是混進了實作細節，或同時寫給太多讀者（本章〈寫給誰看〉會談）。

## 取捨

- 骨架是起點，不是表單。小改動每段只剩一句話，填空填出來的是形式；輕量版的做法，本章〈[什麼時候需要寫](01_when_to_write.md)〉談過。
- 方向都還沒定時，自由格式的筆記或 prototype 比骨架有用；方向有了，再套骨架。
- 段落名稱可以換（「動機」「提案」）；團隊已有範本就用範本，重點是每個問題都有人回答。
- 骨架的順序是讀的順序，不是寫的順序：常見的是先寫目標與非目標，再寫方案，最後回頭補背景。
- 目標寫得太細，文件變成規格書，每次調整都要重新同意；非目標列太多，像在推托。

## 重點整理

- 設計文件的每一段回答一個問題：背景（為什麼、有什麼限制）、目標、非目標、方案、替代方案、取捨、風險、上線與回復、未決問題。
- 目標要能用數字檢驗；非目標寫「有人會期待、這次不做」的事，用來擋範圍蔓延。
- 方案寫需要同意的決定，不寫實作細節；判斷標準是改了它要不要重新取得 reviewer 的同意。
- 取捨要寫出被接受的缺點，並對照目標；風險與未決問題照實寫，讓 reviewer 知道該評估什麼。
