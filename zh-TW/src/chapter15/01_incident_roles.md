# 事故中的角色分工

## 本集目標

判斷事故發生時誰宣告、誰做決定、誰調查、誰對外、誰記錄：事故指揮官做決定但不親自除錯，其他角色各管一件事；小團隊一人身兼多職時，哪幾件事不能合併；不確定嚴重程度時，先宣告再降級。

## 情境

虛構的活動報名平台上，第 14 章設計的提醒 worker 上線了。依第 14 章〈[設計文件的 review](../chapter14/05_design_review.md)〉的結論，worker 先跑在報名服務的行程內，由設定開關控制是否啟動。

這次事故的經過（時間與數字都是虛構的教材範例）：T+0 分部署新版本，正好遇到熱門活動的提醒批次；記憶體開始持續上升。T+40 分，報名服務的容器超過記憶體上限被終止，重啟後又再上升，報名 API 開始出現大量 5xx。T+45 分，錯誤預算消耗速度的告警通知值班工程師（第 9 章〈[SLI 與 SLO](../chapter9/08_sli_slo.md)〉談過，告警看消耗速度，而不是看單一個 5xx）。當時沒有人知道原因，書上留到本章〈用 `pprof` 與 trace 在現場診斷〉才揭曉。

這集只談 T+45 分到 T+60 分、事故指揮官決定止血之前這 15 分鐘的協作。止血選哪個選項，本章〈先止血，再找原因〉會談。

## 沒有分工的 15 分鐘

下面是沒有人宣告、沒有人分工時，頻道裡常見的樣子（節錄，是假設的版本，不是這次事故的紀錄）：

```text
值班工程師：（貼圖：錯誤率曲線）報名 API 的 5xx 一直在上升，有人在看嗎？
維護者：（貼圖：容器記憶體曲線）記憶體一直爬，T+40 分被終止過一次
提醒 worker 的作者：（貼圖：worker 的送出數量）會不會是 GC 壓力？
行動 App 團隊的工程師：（貼圖：閘道逾時次數）閘道的逾時是不是設太短？
產品負責人：（貼圖：報名成功數）報名數掉得很明顯，是不是前端壞了？
客服：使用者一直問報名失敗怎麼辦，可以回什麼？
值班工程師：先把閘道的逾時設定改回舊值。
維護者：資料庫連線池的上限剛剛也改回舊值了。
提醒 worker 的作者：兩個都改了？現在線上到底是哪一份設定？
值班工程師：不確定，錯誤率看不出有沒有變。
（之後又是一串圖表與猜測，客服的問題沒有人回。到 T+60 分，頻道裡沒有任何決定。）
```

每個人都在做有道理的事，合起來卻出了四個問題：

- **沒有人決定。** 沒有人說「這是事故」，也沒有人負責在資訊不夠時選一條路。
- **五個人看不同的東西。** 五張圖、四種猜測，沒有人整理哪些是已知、哪些只是猜的。
- **兩個變更同時進行。** 兩個設定都改了，也都沒有生效的證據，沒有人知道線上是哪一份設定；之後錯誤率變了，也歸不了因。
- **沒有人對外。** 客服只能自己編說法，使用者收到的訊息各不相同。

## 四個角色與宣告

宣告事故只是在頻道說一句話，把「大家一起看」換成「有人負責」。任何人都可以宣告，不必等主管同意；告警叫醒的值班工程師預設是第一任事故指揮官。宣告時一併指派角色：

| 角色 | 負責 | 不做 |
| --- | --- | --- |
| 事故指揮官 | 定嚴重程度、指派角色、聽取回報、做決定、定期整理現況 | 不親自除錯、不親自改設定 |
| 調查者 | 找出發生了什麼事、有哪些選項，回報已知與未知 | 不自己改設定，要改先向指揮官報告 |
| 對外溝通 | 客服、使用者與相關團隊的唯一出口：已知的事實與下次更新的時間 | 不猜原因、不承諾修好的時間 |
| 記錄者 | 在頻道記時間軸：何時發現、誰決定了什麼、誰改了什麼 | 不參與討論 |

其他人是支援：待命，被指揮官點名才回答，新的發現交給調查者。指揮官不需要是最懂技術的人，要的是不被細節吸走：一旦自己動手除錯，就沒有人在看全局了。

## 同一段時間，有分工的版本

這次事故的實際經過是有分工的版本。T+45 分宣告之後，頻道長這樣：

```text
T+45  值班工程師：宣告事故，2 級（分級見「小團隊、分級與什麼時候宣告」的表）。報名 API 部分請求失敗，原因不明。先由值班工程師擔任事故指揮官。
      所有討論只在這個頻道；貼圖請附一句「這張圖說明什麼」。
      指揮官：調查者＝提醒 worker 的作者；對外溝通＝產品負責人；記錄者＝行動 App 團隊的工程師。
      維護者與其他人待命。設定變更先在頻道說，指揮官說「可以」才動，一次只改一件。
      對外溝通 → 客服：「報名功能目前部分使用者會失敗，團隊處理中，請使用者稍後再試。下次更新 5 分鐘後。」
每 5 分鐘  指揮官：現況（格式見下）
T+60  指揮官：決定關掉提醒 worker 的設定開關。重啟之前，調查者先收 goroutine 與 heap profile，收完回報。
      記錄者：T+60 決定關掉 worker 開關，重啟前先收 profile。
T+70  指揮官：錯誤率回到正常，宣告止血。
      對外溝通 → 客服與使用者：「影響已解除，原因調查中。」
```

T+60 分的決定，理由在本章〈先止血，再找原因〉會談；現場怎麼收證據，本章〈用 `pprof` 與 trace 在現場診斷〉會談。這裡要看的是：兩個變更不會同時進行、客服有一句統一的話、時間軸有人記，而且有一個人在 T+60 分之前一直負責「什麼時候該決定」。

## 指揮官的現況與交接

指揮官的固定動作是整理現況，用一個固定格式，每 5 分鐘一則，把已知與未知分開：

```text
現況（指揮官，每 5 分鐘一則）
影響：報名 API 部分請求回 5xx，錯誤預算持續消耗。
已知：T+0 分部署新版本；記憶體自部署後持續上升；T+40 分容器被終止過一次。
未知：記憶體上升的原因。
進行中：調查者查原因；對外溝通通知客服；記錄者記時間軸。
需要決定：要不要止血、用哪個選項。
下次更新：5 分鐘後。
```

「需要決定」那一行把決定攤在所有人面前，不會拖到沒有人記得有這件事。後來才加入的人讀最新一則現況就跟得上，不必翻頻道。

事故拖長，指揮官會累，或更適合的人加入。交接要在頻道裡明說，兩邊都回應，中間不能有沒人指揮的空檔：

```text
舊指揮官：交接給〔某人〕。現況：（貼最新一則）。進行中：……。待決定：……。
新指揮官：接手。
舊指揮官：確認。從現在起由新指揮官指揮。
```

## 小團隊、分級與什麼時候宣告

小團隊沒有五個人可以分。保留的不是人數，而是不能合併的那幾件事：

- **指揮與除錯要分開。** 兩個人就是一個指揮、一個調查；指揮的可以是比較不懂技術的那位，只負責問「已知什麼、未知什麼、要決定什麼」。
- **記錄者可以由頻道代替。** 每個動作都先在頻道寫一行，時間戳就是時間軸。
- **對外溝通可以併入指揮官。** 條件是固定一個頻率、說一句話，不在除錯的空檔隨口回覆。
- **只有一個人時，仍然宣告。** 宣告是為了把第二個人叫來；在他到之前，每 10 分鐘停下來，把現況與下一個決定寫在頻道，這個人就輪流戴指揮官與調查者的帽子。

這次事故有五個人，是比較好的情況。嚴重程度用影響分成三級，下面是教材範例的定義，各團隊依自己的服務調整：

| 級別 | 影響 | 回應 |
| --- | --- | --- |
| 1 級 | 報名等核心功能對大多數使用者不能用，或有資料遺失 | 全員、立刻對外公告 |
| 2 級 | 核心功能部分失敗或明顯變慢，或消耗速度告警響了 | 指揮官與調查者，指派對外溝通 |
| 3 級 | 次要功能受影響，或有替代做法 | 上班時間處理，不需要正式角色 |

這次事故是 2 級：報名 API 部分請求失敗，錯誤率最高約四成。拿不準幾級，或不確定影響範圍，或需要第二個人幫忙，或得動正式環境的設定與版本，就宣告，先定高一級，查清楚再降級。涉及資安的事故（資料外洩、遭入侵）通報與鑑識的流程不同，這一章不談。

## 取捨

- 分工有成本：指揮官不除錯，最會除錯的人少了一雙手，人少時最明顯。換來的是決定有人負責、變更不會同時進行。
- 常見的「大家一起看」在小事上是對的：只有一個人、原因明顯、五分鐘能解決的 3 級小事，宣告與四個角色是多餘的。判斷的依據是分級，不是儀式。
- 「寧可早宣告」不等於什麼都宣告：每次都叫醒一群人，值班的人會學會忽略。用分級控制誰被叫來，3 級不叫人。
- 角色很容易變成形式：宣告時只寫「請指派角色」，沒有任何人接手，頻道還是原來那樣。要說出具體的人，被指派的人要回應。
- 記錄者寫下的時間軸，事後會用在檢討，本章〈事後檢討（blameless postmortem）〉會談；那時看的是系統怎麼讓事情發生，不是誰做錯了什麼。

## 重點整理

- 沒有分工的頻道，五個人各看各的、兩個變更同時進行、客服沒有人回、沒有人決定。
- 宣告事故是一句話，任何人都可以說；值班工程師預設是第一任指揮官，宣告時一併指派調查者、對外溝通、記錄者。
- 指揮官做決定、整理現況（已知、未知、需要決定），不親自除錯；交接要在頻道裡明說，兩邊都回應。
- 小團隊保留指揮與除錯分開；記錄者可以由頻道代替，一個人時也要宣告並定時寫下現況。
- 拿不準就宣告，先定高一級再降級；分級決定誰被叫來，小事不需要四個角色。
