# 事後檢討（blameless postmortem）

## 本集目標

事故止血之後寫事後檢討，問的是「系統為什麼允許這件事發生」，而不是「誰做錯」；並能照摘要、影響、時間軸、原因、做得好、運氣好、行動項目的順序寫出一份。blameless 不是沒有責任，是把責任放在改善系統。

## 情境

提醒 worker 的事故在 T+70 分止血，報名 API 的錯誤率回到正常，調查者也從 profile 確認了原因（現場怎麼收，本章〈[用 `pprof` 與 trace 在現場診斷](03_pprof_trace_live.md)〉談過）。事故中的分工見本章〈[事故中的角色分工](01_incident_roles.md)〉，為什麼先關開關而不是回復版本，見本章〈[先止血，再找原因](02_mitigate_first.md)〉。

現在事故指揮官要在幾天內開檢討會、交出一份檢討文件。這一集談這份文件：它是本章唯一一份完整的檢討，標明是教材範例，其他集只回頭引用需要的部分。

## 追究責任的檢討

檢討會一開場就問「是誰沒設逾時」，會後的文件常常長這樣：

```text
根本原因：提醒 worker 的作者沒有為推播呼叫設逾時，也沒有限制 goroutine 數量。
行動項目：
1. 提醒 worker 的作者以後要更小心。
2. 所有人 review 時多注意逾時。
```

每一句都是事實，卻改變不了任何東西：下一位寫對外呼叫的人，面對的還是同一個系統，沒有東西提醒、也沒有東西擋下。

代價出在下一次事故。假設那時第一個認出是自己那次變更的人，選擇先不說，等調查者自己翻到部署紀錄才承認。細節每晚到一分鐘，錯誤率就多上升一分鐘。檢討若讓說出細節的人付出代價，大家學到的是藏起來，不是把系統補好。

## 把問題從「誰」換成「系統」

換個問法：作者當時看到什麼，為什麼那樣寫是合理的？哪一道防線本來可以擋下，卻沒有？問題分成三組，對應範例「原因」的三個標題：

- 為什麼系統允許這個錯誤進入正式環境？設計、review、測試、壓測各是一道防線。
- 為什麼沒有提早被發現？看告警與儀表板。
- 為什麼影響擴大、拖長？看部署的結構，以及事故中的分工與決定。

「五個為什麼」是常見的追問方式，它有兩個限制：

```text
報名 API 為什麼失敗？    容器被終止。
為什麼被終止？           記憶體超過上限。
為什麼超過？             goroutine 不斷累積。
為什麼累積？             推播的 HTTP 呼叫沒有逾時。
為什麼沒有逾時？         作者沒設。
```

第一，它只走一條鏈。review 沒抓到、壓測沒模擬慢的供應商、沒有 goroutine 告警、worker 與報名 API 共用行程，各是另一條鏈，這次事故的原因不只一條。第二，最後一問很容易停在人身上，停在這裡就成了追究責任。把最後一問改成「為什麼系統允許沒設逾時的呼叫上線」，鏈才會分岔。五是慣例，不是定數：問到系統的防線就停，分岔就分別問。

## 範例：blameless 的事後檢討

下面是這次事故的檢討，是教材範例，平台、事故與數字都是虛構的。摘要讓沒參加的人讀完就懂；時間軸只寫事實，由記錄者的紀錄整理；原因寫系統因素，不寫人；行動項目只列出，怎麼寫本章〈行動項目與追蹤〉會談。

```text
事後檢討：提醒 worker 拖垮報名服務（教材範例，平台、事故與數字皆為虛構）
整理：事故指揮官（值班工程師）。參加：調查者（提醒 worker 的作者）、對外溝通（產品負責人）、記錄者（行動 App 團隊的工程師）、維護者、客服。

## 摘要
新版本把推播改成直接呼叫供應商。供應商變慢後，goroutine 不斷累積，報名服務的容器因記憶體超過上限被終止，
報名 API 部分失敗約 30 分鐘。關掉提醒 worker 的設定開關後恢復。

## 影響
- 報名 API：T+40 到 T+70 分部分失敗，錯誤率最高約四成。
- 提醒：該批提醒沒有自動補寄（預定時間後 1 小時仍失敗就放棄，記成失敗數），也沒有重複寄送（冪等紀錄有效）。
- 要不要人工補寄、怎麼補，尚未決定（行動項目 5）。

## 時間軸
T+0       部署新版本，遇到熱門活動的提醒批次。
T+0 之後  供應商回應變慢，goroutine 卡在等回應，記憶體上升。沒有 goroutine 與記憶體的告警。
T+40      容器超過記憶體上限被終止，重啟後又上升；報名 API 大量 5xx。
T+45      錯誤預算消耗速度告警通知值班工程師，宣告事故。
T+45～60  多人同時除錯，兩人回復了不同的設定。調查者認為要先找到根本原因；當時沒有約定何時先止血。錯誤率持續上升。
T+60      事故指揮官決定先關掉 worker 的設定開關，不回復版本（同一版本含已對外公告的修正）。重啟前調查者收了 goroutine 與 heap profile。
T+70      錯誤率回到正常，宣告止血。
之後      從 profile 確認原因：HTTP 呼叫沒有逾時，每則提醒一個 goroutine、沒有上限。

## 原因
為什麼系統允許這個錯誤進入正式環境：
- 沒有機制要求對外呼叫有逾時與並行上限。review 檢查清單有這一項，這個 PR 沒有套用。（行動項目 1）
- 壓測沒有模擬慢的供應商，慢的下游從沒在測試中出現過。
為什麼沒有提早被發現：
- 沒有 goroutine 與記憶體的告警。T+45 響的是錯誤預算消耗速度，使用者已經受影響；「預定時間已過、仍未寄出」的告警以 1 小時期限為準，批次 T+0 開始，最早 T+60 之後才可能響，比 T+45 的告警晚，幫不上這次的偵測。（行動項目 2）
為什麼影響擴大、拖長：
- worker 與報名 API 共用行程。ADR-0012 的後果寫過這個風險，是接受過的取捨；事故顯示代價比當時估計的大。（行動項目 3）
- 設定開關從未演練，值班只看到告警、沒有 runbook，也沒有先止血的約定。（行動項目 4、6）

## 做得好
- 錯誤預算消耗速度告警在 5xx 開始後約 5 分鐘通知值班工程師。
- 寄出之前先寫冪等紀錄：容器被終止、重啟後，都沒有重複寄送。
- 事故指揮官選設定開關而不是回復版本，保住已公告的修正；重啟前先收 profile，原因是用證據確認的，不是猜的。

## 運氣好
- T+60 收 profile 時供應商仍然很慢。若它先恢復，卡住的 goroutine 會自己結束，現場就沒了。
- 設定開關從來沒有演練過，這次剛好能用。

## 行動項目
1. 對外呼叫加上逾時與並行上限，附一個會失敗的測試。
2. goroutine 數量與 heap 的告警。
3. 把 worker 拆成獨立部署，開新 ADR 取代 ADR-0012。
4. 演練設定開關。
5. 決定超過期限的提醒要不要補寄、由誰判斷；不補就明說是接受的風險。
6. 寫「提醒 worker 記憶體或 goroutine 持續上升」的 runbook。
```

原因逐條對得上本書談過的判斷。review 清單的第 16 項「每個對外的呼叫都有逾時」，就是這次沒被套用的那一項，見第 13 章〈[Go 程式碼的 review 檢查清單](../chapter13/02_go_review_checklist.md)〉。清單只是提醒，PR 沒套用就不會被問到，所以行動項目 1 要附會失敗的測試，不靠人記得。worker 與報名 API 共用行程，是第 14 章〈[設計文件的 review](../chapter14/05_design_review.md)〉明講過的取捨，後果也寫進 ADR-0012，第 14 章〈[設計文件與 ADR 的關係](../chapter14/06_design_doc_and_adr.md)〉談過。這是接受過的風險，不是遺漏。舊 ADR 的內文不改，所以要開新 ADR 取代它。一個下游拖垮其他功能的結構，第 10 章〈[bulkhead](../chapter10/08_bulkhead.md)〉談過，這次壞的是 worker，受害的是報名 API。

「做得好」與「運氣好」要分開寫：前者下次還做得到，後者沒有人保證。運氣好的項目多半該變成行動項目，像開關沒演練過，就是行動項目 4。

## blameless 不等於沒有責任

- 責任在改善系統：每個行動項目都有負責的角色，做不做完會被追蹤。blameless 免除的是「為過去的判斷受罰」，不是「為改善負責」。
- 提醒 worker 的作者是最懂那段程式的證人，也常是行動項目 1 的負責人；作者說得出當時的考量，檢討才找得到防線的缺口。
- blameless 的前提是判斷在當時的資訊與壓力下合理。刻意繞過規則、隱瞞事實，是另一件事，由管理處理，不在檢討文件裡。

## 檢討會怎麼開、文件給誰看

- 時機：止血後的幾天內，細節還查得到、記憶還在；不要拖到一個月後，也不在止血當天，大家還在恢復。
- 主持：最好不是事故中做決定的人，例如由記錄者主持。主持人先說規則：問系統，不問人。
- 順序：先用時間軸對事實，每個決定問「當時看到什麼」，再談原因、做得好與運氣好，最後只列行動項目。
- 用語：「忘了」「疏忽」「應該要」改成「沒有機制擋下」「沒有告警」；原因的主詞是系統。
- 讀者：整個工程團隊、產品負責人與客服都看得到，不只參加者；別的團隊讀了，才會去檢查自己的服務有沒有同樣的洞。對使用者另寫一份短的說明，由對外溝通負責，不直接貼這份。

## 取捨

- 完整的檢討要花一場會加一份文件。小事故用短版就夠：摘要、原因、行動項目；寧可早宣告再降級的事故，降級後不必寫完整版。
- blameless 靠信任。檢討之後，若主管私下仍問「到底是誰」，文件寫得再中性也沒用。
- 追究個人在有些地方是對的：刻意繞過安全控制或隱瞞事實時，要處理人；但仍要問系統為什麼讓繞過成為可能。
- 檢討找得到的原因，只是參加的人想得到的；它降低同類事故再發生的機會，不消除。
- 檢討寫完、行動項目沒有人追，就白寫了。怎麼寫、怎麼追，本章〈行動項目與追蹤〉會談。

## 重點整理

- 追究責任的檢討以「作者要更小心」收尾，改變不了系統，還讓下一次事故的細節更晚被說出來。
- blameless 的檢討問「系統為什麼允許」，分成進入正式環境、沒有提早發現、影響擴大三組；五個為什麼只走一條鏈，要在防線處分岔。
- 完整的檢討有摘要、影響、時間軸、原因、做得好、運氣好、行動項目；時間軸只寫事實，原因的主詞是系統。
- blameless 不等於沒有責任：責任在改善系統，每個行動項目有負責的角色；刻意繞過規則另外處理。
- 檢討會在止血後幾天內開，主持人不是做決定的人；文件給整個團隊看，對使用者另寫短版說明。
