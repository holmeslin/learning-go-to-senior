# 先止血，再找原因

## 本集目標

事故中，先選一個夠快、範圍夠小、能回頭、而且看得出有沒有效的動作，把影響壓下來，再去找根本原因：知道回復版本、設定開關、擴充資源、卸載負載各自的速度、風險與副作用，在不確定時做得出決定。

## 情境

虛構的活動報名平台（平台、事故與數字都是教材範例，文中的人一律用角色稱呼）上，第 14 章設計的提醒 worker 先跑在報名服務的行程內，用設定開關控制是否啟動。新版本把推播改成直接呼叫供應商的 HTTP API，部署（T+0）時正好碰上熱門活動的提醒批次。T+40 分，報名服務的容器超過記憶體上限被終止，重啟後記憶體又開始上升，報名 API 出現大量 5xx。T+45 分，SLO 的錯誤預算消耗速度告警通知值班工程師，值班工程師宣告事故（2 級）。T+45 到 T+60 實際上沒有分工，那段經過與改寫成有分工的版本，本章〈[事故中的角色分工](01_incident_roles.md)〉談過。T+60 分起，值班工程師以事故指揮官的身分做決定，調查者是提醒 worker 的作者，對外溝通是產品負責人。這集看接下來的決定：動手之前先做什麼、動哪一個。

## 先找原因的 20 分鐘

事故宣告之後沒有人分工，提醒 worker 的作者（後來的調查者）第一反應是找出為什麼。頻道裡的對話長這樣（時間是相對時間；T+60 之前還沒有人被指派角色，所以用各人原本的身分稱呼）：

```text
T+50 提醒 worker 的作者：記憶體從部署後一路往上，T+40 被殺過一次，重啟後又在爬。新版本、推播供應商、那批提醒的量，三個都有可能，還分不出來。
T+55 值班工程師：錯誤率還在上升，現在能不能先處理？
T+55 提醒 worker 的作者：現在動手是亂猜。重啟會把現場清掉，關了又不知道是不是真的有效。再給我一點時間，找到原因再處理。
T+60 事故指揮官：不再等，決定在下面。
```

作者的謹慎有道理：沒確認原因就動手，可能動錯，白白損失時間。但從 T+40 分第一批 5xx 到 T+60 分，錯誤率一路上升了 20 分鐘，這段時間報名持續失敗，錯誤預算（第 9 章〈[SLI 與 SLO](../chapter9/08_sli_slo.md)〉）也持續消耗。當時沒有人約定「找多久還找不到就先止血」，所以每一次「再給我一點時間」聽起來都合理。

止血與找原因要的東西不同。找原因要證據，慢，而且不保證在這一刻找得到；止血只要三樣：一個嫌疑（最近改了什麼、症狀對得上誰）、一個動作、一個看得出有沒有效的指標。這次三樣都有：症狀都出現在部署之後，嫌疑在新版本的提醒 worker；動作是下一段的選項；指標是 5xx 錯誤率與記憶體曲線。止血是一個假設加上一段觀察，沒效就換下一個動作，不必等到確定。

## 止血的四個選項

每個動作問四件事：多快有效、能不能回頭、影響多大、有什麼副作用。

| 選項 | 多快有效 | 風險與副作用 | 這次事故 |
| --- | --- | --- | --- |
| 回復到上一個版本 | 部署流程跑多久就多久；要先知道上一個版本是哪一個 | 同一個版本裡的其他變更一起退回；資料或設定已經往前走時，舊版未必接得住 | 新版本還包含一個已對外公告的修正，回復會把它一起收回 |
| 用設定開關關掉新功能 | 改設定、重啟，設定在啟動時讀一次 | 只影響那個功能；要確認每個實例都生效，開關沒演練過就可能無效 | 報名 API 不動，只暫停提醒 |
| 擴充資源 | 平台支援的話最快 | 原因還在，只是延後撞到上限；多出來的實例一樣帶著 worker | 記憶體上限拉高，只讓下一次被終止晚一點 |
| 卸載負載 | 入口已經有門檻的話立刻 | 連正常的請求也被拒絕 | 壓力來自行程內的 worker，不是請求量，入口再擋也止不住 |

設定在啟動時讀一次、改了要重啟，是第 12 章〈[設定與環境變數](../chapter12/08_config_env.md)〉的做法。擴充資源只是延後撞到上限：這次活著的資料持續增加，卡住的 goroutine 與它們持有的資料都還活著，加大上限只買時間。`GOMEMLIMIT` 是軟上限、活著的資料收不掉，第 8 章〈[`GOMEMLIMIT` 與容器記憶體上限](../chapter8/03_gomemlimit_container.md)〉談過。卸載負載對付的是請求太多，第 10 章〈[負載卸載與降級](../chapter10/07_load_shedding.md)〉談過；這次的壓力不是從入口進來的。

## 指揮官為什麼選開關

指揮官的決定寫在頻道裡，讓每個角色看得到：

```text
T+60 事故指揮官：決定：關掉提醒 worker 的設定開關，不回復版本。
  理由：症狀都出現在部署之後，嫌疑在 worker；新版本、供應商、提醒的量，worker 一停三個都停手。
        開關只影響提醒，報名不動；回復會把已對外公告的修正一起收回。
  順序：保留現場，再改設定、重啟；一次只動這一個。
  驗證：報名 API 的 5xx 回到平常，重啟後記憶體不再上升。開關沒效，才改回復版本。
```

這個選擇不是因為開關比較高明，而是它在四項裡最小、最能回頭：打開開關就恢復，也不必再對外更正。設計文件的「上線與回復」本來就寫「出問題就關掉開關」（第 14 章〈[結構：背景、目標、非目標、方案、取捨](../chapter14/02_doc_structure.md)〉），設計 review 時大家同意過，事故中不必再爭退路。

代價要講明：提醒暫停，而且依第 14 章的設計，預定時間後 1 小時仍失敗的提醒就放棄、記成失敗數，這批不會自動補寄，也不會重複寄送。「寧可不寄，也不重複」在這次事故裡真的發生了；要不要人工補寄，本章〈事後檢討（blameless postmortem）〉與〈行動項目與追蹤〉會談。

重啟前先保留現場，是因為重啟會清掉證據；怎麼收，本章〈用 `pprof` 與 trace 在現場診斷〉會談。關掉 worker 在效果上是一種降級：保住報名、暫停提醒。降級要讓人看得到，所以對外溝通要在公告補上「提醒暫停」，客服拿到同一句話。

## 先確認版本，再確認止血有效

決定回復或不回復之前，要知道線上每個實例跑的是哪個版本、兩個版本之間差了什麼。第 12 章〈[`go build` 與用 `-ldflags` 注入版本](../chapter12/01_build_version_info.md)〉談過，版本從執行檔自己來：服務提供 `/version` 端點、啟動時把版本印進日誌，或對執行檔跑 `go version -m` 看 `vcs.revision`；`vcs.modified=true` 表示不是乾淨的 commit。部署進行到一半時，不同實例可能跑不同版本，要逐一確認。有了 commit，才列得出兩版之間的變更清單：

```text
T+58 提醒 worker 的作者：每個實例都是新版本。兩版之間的變更，除了推播改成直接呼叫供應商，還有那個已公告的修正。
```

改了設定、重啟之後，看兩類指標：

- 症狀：報名 API 的 5xx 錯誤率回到平常；SLO 的消耗速度，短窗口先降下來，長窗口還會高一陣子。
- 原因：worker 真的停了（每個實例的日誌看得到沒有啟動、寄出數不再增加），記憶體曲線不再上升。看斜率，不看數值：剛重啟的記憶體本來就低，那是重啟的效果，不是開關的效果。

等多久：至少等一個短窗口走完，並且過一次掃描。沒生效的實例，下一次掃描（每 5 分鐘一次）就會讓記憶體重新上升。另外，第 14 章〈[設計文件的 review](../chapter14/05_design_review.md)〉加進目標的「預定時間已過、仍未寄出」告警以 1 小時期限為準，這批從 T+0 開始，最早 T+60 之後才可能響，比 T+45 的錯誤預算告警晚。關掉 worker 之後，這個告警的數字會持續增加。這是預期的結果，不是止血失敗，指揮官要先在頻道說明，免得被當成新的故障。T+70 分，錯誤率回到正常，指揮官宣告止血。

## 止血之後才找原因

宣告止血不是結案。調查者拿保留的現場找根本原因，指揮官把狀態改成「已止血，調查中」；開關重新打開，要等修正上線，並照設計文件先在一部分活動啟用。

止血用的變更，review 可以從簡：設定開關與回復版本是已經存在的做法，指揮官決定、第二個人看過就執行。若止血需要緊急 PR，先放行：每多等一輪 review，使用者就多受影響一段時間。缺的測試與檢查補在後續，並開 issue 追蹤，issue 怎麼寫，見第 13 章〈[什麼時候該擋、什麼時候可以放行](../chapter13/06_block_or_approve.md)〉的「放行之後」。

## 取捨

- 止血的假設可能錯。開關關了、5xx 沒降，就承認，改回復版本，不要因為已經花了時間在這個選擇上就再等。
- 調查者的謹慎在有些情況下是對的：動作不可逆（刪資料、強制重建）或會擴大傷害時，先確認再做。可回頭的動作才適合先做再看。
- 開關要事先存在，而且演練過。這次的開關從沒演練過，剛好能用；沒演練過的開關，關了沒效時就只剩回復或趕著修正再上線。演練的事，本章〈行動項目與追蹤〉會談。
- 回復版本在有些情況反而是對的：不知道是哪個功能壞了、變更小又沒有要保留的修正、部署流程很快。這次不選它，是因為有更小的動作，而且回復會收回已公告的修正，不是因為回復比較差。
- 擴充資源只適合買時間，例如開關還沒確認能用、需要多幾分鐘。

## 重點整理

- 事故中第一個問題是怎麼讓影響停下來，不是為什麼；止血只需要一個嫌疑、一個動作、一個看得出有沒有效的指標，不需要根本原因。
- 選動作看速度、能不能回頭、影響範圍與副作用：回復、設定開關、擴充資源、卸載負載各有適用的時候；不確定時選最小、可回頭的。
- 這次事故選關掉 worker 的開關，不回復版本：影響只在提醒，也不收回已公告的修正；代價是這批提醒不會自動補寄。
- 動手前確認線上版本與兩版差異；動手後用症狀與原因兩類指標確認，至少等過一個短窗口與一次掃描。
- 重啟前先保留現場，止血之後才找根本原因；止血用的變更 review 從簡，缺的補在後續並開 issue。
