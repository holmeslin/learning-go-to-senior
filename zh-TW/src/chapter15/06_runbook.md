# runbook

## 本集目標

告警響的時候，值班的人手上要有一份短的、每一步都能直接執行的 runbook：先確認、保留現場、止血，不行就升級。這集判斷它該寫什麼、放在哪裡，以及怎麼讓它一直可用。

## 情境

提醒 worker 的事故過後，事後檢討列了行動項目 6：寫「提醒 worker 記憶體或 goroutine 持續上升」的 runbook（本章〈[事後檢討（blameless postmortem）](04_blameless_postmortem.md)〉）。負責的是提醒 worker 的作者，完成的定義是告警連得到它，而且沒參與事故的另一位值班工程師照著做一遍，能完成確認、保留現場、止血（本章〈[行動項目與追蹤](05_action_items.md)〉）。事故當天沒有這份文件：T+45 分響的是錯誤預算消耗速度告警，值班工程師只看到告警，沒有 runbook，也沒有先止血的約定。平台與數字都是虛構的教材範例，人用角色稱呼。

## 沒有 runbook 的告警

假設 goroutine 與 heap 的告警（行動項目 2）先上線，runbook 還沒寫完；某個夜裡告警響了。下面是假設的版本，不是這次事故的紀錄：

```text
告警：報名服務的 heap 持續上升。（沒有連結，沒有說明。）
值班工程師：heap 在上升，是 worker 嗎？要看哪裡？
值班工程師：能先重啟嗎？搜尋頻道，找上次的做法。
（頻道裡是事故當天的幾百則訊息：圖表、猜測、被改回去的設定。有一則寫「重啟前先收 profile」，沒寫怎麼收、收到哪裡。）
值班工程師：上次是誰在處理？該找誰？
（20 分鐘後，值班工程師重啟。記憶體掉回去，現場也沒了。）
```

告警只說「高」，其他四件事都沒有答案：

- **代表什麼、影響什麼。** 不知道是不是 worker，也不知道會不會拖垮報名 API。
- **能不能重啟。** 重啟會清掉卡住的 goroutine 與 heap，本章〈[用 `pprof` 與 trace 在現場診斷](03_pprof_trace_live.md)〉談過。
- **找誰。** 靠記憶，記不得就問頻道。
- **上次怎麼做。** 埋在聊天紀錄裡，混著沒有採用的做法。

## 一份 runbook

下面是這份 runbook，放在告警連結指向的頁面（〔〕是要填的空格）。指令都是本章〈[用 `pprof` 與 trace 在現場診斷](03_pprof_trace_live.md)〉的重現腳本實際執行過的，只有診斷位址不同：`127.0.0.1:18150` 是書附範例的本機位址，服務的 runbook 換成它的診斷位址，診斷位址只開給內部。

> **Runbook：提醒 worker 記憶體或 goroutine 持續上升**（教材範例）
>
> 維護：提醒 worker 的作者。最後演練：〔日期〕，由沒參與撰寫的值班工程師照著做完；下次：〔日期〕。
>
> - **代表什麼：** 提醒 worker 對推播供應商的呼叫卡住，goroutine 與記憶體累積；容器超過記憶體上限會被終止，重啟後又上升，報名 API 跟著失敗。
> - **影響：** 報名 API 部分失敗。預定時間後 1 小時仍失敗的提醒就放棄、記成失敗數，不會自動補寄，也不會重複寄。
>
> **1. 確認（值班工程師，約 1 分鐘）**
>
> 對告警指出的那個實例，看 goroutine 總數，隔 1 分鐘再看一次：
>
> ```bash
> curl -s 'http://127.0.0.1:18150/debug/pprof/goroutine?debug=1' | head -n 1
> ```
>
> 輸出是 `goroutine profile: total N`。平常的 N 約〔填〕。
>
> - N 偏高又在上升：找調查者（見第 4 步）一起往下做，他到之前第 2 步由值班工程師先做。
> - 報名 API 的 5xx 已經上升，或消耗速度告警也響了：在事故頻道宣告 2 級，自己擔任事故指揮官並指派角色；拿不準也宣告。
> - 對不上這個症狀（例如 CPU 高、N 正常）：離開這份 runbook，找調查者。
>
> **2. 保留現場（調查者；時間盒由指揮官定，這份範例用 5 分鐘）**
>
> 重啟與改設定之前先收。由便宜的先收，每份存成檔案，不貼進頻道（檔案有函式名稱與路徑，只給調查者）：
>
> ```bash
> curl -s -o goroutine1.debug1.txt 'http://127.0.0.1:18150/debug/pprof/goroutine?debug=1'
> curl -s -o goroutine1.pb.gz http://127.0.0.1:18150/debug/pprof/goroutine
> curl -s -o heap1.pb.gz 'http://127.0.0.1:18150/debug/pprof/heap?gc=1'
> curl -s -o goroutine1.debug2.txt 'http://127.0.0.1:18150/debug/pprof/goroutine?debug=2'
> # 隔 1 分鐘，再收一次
> curl -s -o goroutine2.debug1.txt 'http://127.0.0.1:18150/debug/pprof/goroutine?debug=1'
> curl -s -o goroutine2.pb.gz http://127.0.0.1:18150/debug/pprof/goroutine
> curl -s -o heap2.pb.gz 'http://127.0.0.1:18150/debug/pprof/heap?gc=1'
> curl -s -o goroutine2.debug2.txt 'http://127.0.0.1:18150/debug/pprof/goroutine?debug=2'
> grep -h '^goroutine profile' goroutine1.debug1.txt goroutine2.debug1.txt
> go tool pprof -top -nodecount=4 -base goroutine1.pb.gz goroutine2.pb.gz
> ```
>
> 第二個總數比第一個大、`-base` 的表有內容，就是還在增加。收完，記錄者在頻道寫「profile 已收」，才進第 3 步；到了時間盒，收到多少都進第 3 步。
>
> **3. 止血（事故指揮官決定，維護者動手；一次只改一件）**
>
> 先關提醒 worker 的設定開關，再重啟。它只影響提醒，可以回頭：
>
> ```text
> 依部署方式改設定：把〔開關名稱〕設為關閉，然後重啟服務。
> ```
>
> 重啟後隔一次掃描（5 分鐘），再跑一次第 1 步的指令。總數不再上升、5xx 回到平常，就是有效；「預定時間已過、仍未寄出」的數量會增加，是預期的，不是失敗。開關沒效（有實例的 worker 還在送、5xx 沒降），才回復版本：
>
> ```text
> 依部署方式回復到上一個版本。先看兩版之間差了什麼，同一版本裡其他的修正會一起收回。
> ```
>
> **4. 升級與找誰**
>
> - 回復版本之後，過了一次掃描，5xx 還是沒降：不要憑一個人試第三個動作，由事故指揮官請調查者與維護者一起看。
> - 核心功能對大多數使用者不能用，或有資料遺失：升 1 級，全員，立刻對外公告。
> - 事故拖長、值班工程師撐不住：在頻道交接，兩邊都回應。
>
> | 角色 | 找誰 |
> | --- | --- |
> | 調查者 | 提醒 worker 的作者 |
> | 對外溝通 | 產品負責人，客服與使用者的說法只有這一個出口 |
> | 記錄者 | 行動 App 團隊的工程師，推播供應商的串接原本由他們維護 |
> | 維護者 | 待命，動手改設定 |
>
> 聯絡方式：〔值班表〕。

第 1、2 步的指令是重現腳本實際執行過的；兩次快照隔多久、時間盒多長，是這份範例自己定的，演練時依累積的速度調整。第 3 步的兩步不在書附範例裡：範例沒有 worker 的設定開關，重現腳本也不部署、不回復版本，驗證不了，所以寫成「依部署方式改設定」，不寫成一行沒人跑過的指令。2 級與 1 級的定義是本章〈[事故中的角色分工](01_incident_roles.md)〉的教材範例，各團隊依自己的服務調整。設定怎麼讀、為什麼改了要重啟，見第 12 章〈[設定與環境變數](../chapter12/08_config_env.md)〉；為什麼先開關、後回復，見本章〈[先止血，再找原因](02_mitigate_first.md)〉。服務自己的 runbook 要把這兩步寫成部署方式下實際的指令，並演練過才算數。找卡在哪一行、要不要收 trace，是調查者止血之後的事，用存下來的檔案做，本章〈[用 `pprof` 與 trace 在現場診斷](03_pprof_trace_live.md)〉談過，不放進 runbook。

## 讓它一直可用

- **短。** 一份 runbook 對應一個告警，第一屏就是代表什麼、影響、第一步。理由與背景連到檢討與本章各集，不抄進來。
- **每一步能直接執行。** 一個動作或一條指令，判斷寫成「如果……就……」，不寫「檢查系統狀態」。位址、檔名填好，讀的人不用替換變數。
- **放在告警連得到的地方。** 告警規則的說明直接附連結，值班的人從告警一步點到；放在 wiki 角落，等於沒有。新服務上線前，告警有沒有附 runbook，是上線前檢查的一項，第 16 章〈[上線檢查表](../chapter16/09_launch_checklist.md)〉談過。
- **定期演練。** 沒參與撰寫的人照著做一遍，卡住的地方就是要改的地方。演練也順便驗證第 3 步：開關真的關得掉（行動項目 4，本章〈[行動項目與追蹤](05_action_items.md)〉的「演練設定開關」）。
- **用過就更新。** 每次用到、每次事故之後，指令、位址、開關名稱、告警門檻或部署方式一變就改。過期的 runbook 比沒有更糟：沒有的人知道自己在猜，照著過期的做的人以為有根據。worker 日後若拆成獨立部署（行動項目 3：要開新 ADR 取代 ADR-0012，本章〈[行動項目與追蹤](05_action_items.md)〉談過），第 3 步與「影響」都要重寫。
- **只自動化查看與收集的步驟。** 第 1 步的數字、第 2 步的兩次快照（一支腳本，檔名帶時間）、止血後的驗證，值得自動化；關不關開關、要不要回復、要不要升級是指揮官的決定，不自動化，尤其不自動重啟，那會把現場清掉。腳本旁仍留一行它做了什麼，腳本壞了還能手動。

## 取捨

- **有維護成本。** 每份都要演練、更新。只為會重複響、步驟固定的告警寫；每次都不一樣的事故寫不出固定步驟，寫成檢討就好。團隊只有兩三個人、告警一年也響不到一次，寫在告警說明裡的三行字，比一份沒人維護的文件實際。
- **事先做的判斷在例外時會誤導。** 「先收現場、先關開關」適合這個症狀，換成別的症狀就不適用。所以第 1 步先確認症狀對不對，對不上就離開。
- **短，就省掉理由。** 每多一個分支，多一個讀錯的機會；省掉的理由放在別處，值班的人要的是下一步，不是教材。
- **照做不等於不用判斷。** runbook 把常見路徑寫死；路徑走不通時，由事故指揮官決定，第 4 步寫明什麼時候升級。
- **演練占時間。** 頻率看變動多快：指令、開關或部署方式剛改過就先演練；很少變的，拉長間隔也比不演練好。

## 重點整理

- 告警只說「高」，值班的人不知道代表什麼、能不能重啟、找誰、上次怎麼做；runbook 回答這四件事。
- 這份 runbook 有四步：確認、保留現場、止血、升級與找誰；先收現場，再改設定、重啟。
- 指令只寫實際跑過的；跑不到的步驟（關開關、回復版本）寫成「依部署方式改設定」，靠演練驗證，不寫成沒人跑過的假指令。
- 短、每步可直接執行、告警連得到、定期演練與更新；過期的 runbook 比沒有更糟。
- 只自動化查看與收集的步驟；要不要止血、升級是指揮官的決定，不自動化。
