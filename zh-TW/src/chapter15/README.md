# 事故處理

服務總有一天還是會出事。這時候缺的往往不是工具，而是判斷：大家同時在一個頻道裡除錯，沒有人做決定，也沒有人對外更新狀態；急著找根本原因，影響持續擴大，其實回復版本或關掉功能幾分鐘就能止血；為了止血直接重啟服務，把唯一能說明原因的現場一起清掉；事後檢討變成追究「是誰沒設逾時」，下一次大家就隱瞞細節；行動項目寫成「以後要更小心」，沒有負責人、沒有期限，三個月後同樣的事故再來一次；告警響了，值班的人不知道第一步該做什麼。

這一章的主題是事故發生時與結束後該做的判斷：怎麼分工、先止血還是先找原因、現場先收什麼證據、事後檢討怎麼寫、行動項目怎麼追蹤、runbook 怎麼寫。全章用同一次事故當例子：虛構的「活動報名平台」上線了第 14 章設計的提醒 worker 之後發生的一次事故。診斷工具本身，第 9 章〈[`/debug/pprof` 與診斷端點](../chapter9/06_debug_pprof.md)〉已經談過，這一章不重講，談的是在時間壓力下怎麼用它們。只有〈用 `pprof` 與 trace 在現場診斷〉有可以在本機重現事故的程式；頻道訊息、時間軸、檢討、行動項目與 runbook 都寫在頁面上。平台、事故與數字都是虛構的教材範例，文中的人一律用角色稱呼。
