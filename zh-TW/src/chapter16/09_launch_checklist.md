# 上線檢查表

## 本集目標

上線前逐項確認提醒服務的檢查表，並判斷哪些項目擋住上線、哪些可以帶著風險上線並開 issue；決定新服務的 runbook 只改哪幾處，以及上線後第一週看什麼、什麼時候刪掉報名服務裡的舊 worker。

## 情境

提醒服務要上線了（平台、數字與日期都是虛構的教材範例，文中的人一律用角色稱呼）。依本章〈[設計文件](01_design_doc.md)〉，報名服務裡的舊 worker 還在送：上線是新服務以開關關閉的狀態部署、關掉舊 worker 的開關、再打開新服務的開關，出問題就反過來。各層的做法，本章之前的集都談過了，這集不教新的做法，只問上線前它們是不是都在、缺了哪一項會怎樣。

書附範例只實作推播；email 走同一套寄送紀錄與重試，差別在供應商的限制是每日額度，範例省略。真的要搬 email 時，額度要另外進壓測與告警。

## 哪些擋住上線

標準是第 13 章〈[什麼時候該擋、什麼時候可以放行](../chapter13/06_block_or_approve.md)〉的三個問題，把「合併」換成「上線」：上線之後會不會有人得到錯的結果、被卡住、被攻擊？這個決定能不能便宜地收回？都不是，就放行並開 issue。

提醒服務上線本身收得回來：關開關，再打開舊 worker。所以擋的有兩類：

- **收回的本事。** 開關演練、回復順序、告警與 runbook、值班的人。缺任何一項，「收得回來」只是設計文件裡的一句話，事故來了才發現關不掉、不知道誰來關。
- **收不回的後果的防線。** 推播送出去就撤不回，記為失敗的提醒不補寄（第 14 章〈[設計文件的 review](../chapter14/05_design_review.md)〉的「寧可不寄，也不重複」）。端對端測試、壓測、秘密與符號層級的弱點，擋的都是這一類。

放行的三項各有理由：套件與模組層級的弱點，程式碼沒有碰到，排進例行升級就夠；告警的門檻沒有真實的流量可以調，先用初始值，改規則不必改服務；`shortcut:` 註解逐條寫了何時升級，風險是已知的。放行要有人簽，格式沿用第 15 章〈[行動項目與追蹤](../chapter15/05_action_items.md)〉的「接受的風險」。內部 API 的契約見本章〈[套件結構與 API](02_packages_and_api.md)〉：

```text
接受的風險：內部 API 沒有驗證，只靠網路邊界
原因：回應只有各狀態的數量，沒有報名者與裝置 token；API 只開在內部網路。
接受的人：產品負責人
重新評估：API 要開給內部網路以外的人之前
```

## 新服務的 runbook 要改的地方

runbook 不重寫。第 15 章〈[runbook](../chapter15/06_runbook.md)〉的四步照用；那一集也說過，worker 拆成獨立部署之後，第 3 步與「影響」要重寫。提醒服務只改下面三處，名稱與服務的設定一致：

| 位置 | 第 15 章的寫法 | 提醒服務 |
| --- | --- | --- |
| 診斷位址 | `127.0.0.1:18150`（範例的本機位址） | `127.0.0.1:6060`，設定是 `REMINDER_DIAG_ADDR`，主機只能是 loopback：指令要在那個實例上執行，或轉發連接埠（第 9 章〈[`/debug/pprof` 與診斷端點](../chapter9/06_debug_pprof.md)〉）。步驟 1、2 的 `/debug/pprof/` 路徑不變，沒有 `cmdline` |
| 影響 | 報名 API 部分失敗 | 報名 API 不受影響，只有提醒不送；預定時間後 1 小時仍沒寄出的記為失敗，不補寄，也不重複 |
| 開關名稱 | 〔開關名稱〕 | `REMINDER_SEND_ENABLED` 改成 `false`，然後重啟（環境變數，啟動時讀一次）；確認啟動日誌 `reminder service started` 的 `send_enabled` 是 `false` |

第 3 步還多出兩件事。第一件是關著的時鐘。開關關閉時服務照常啟動、`/readyz` 回 200，但不掃描、不寫紀錄，`reminder.deliveries`、`reminder.scan.duration`、`reminder.overdue.unsent` 三個指標也不存在：`Dispatcher` 沒有建立，不是變成 0。第 15 章寫的「預定時間已過、仍未寄出」的數量會增加，在這裡看不到，也就沒有東西提醒時間在走。預定時間後 1 小時一到，沒送出的提醒就過期，打開之後的第一次掃描把它們記為失敗、不補寄（本章〈[錯誤與資料層](03_errors_and_data.md)〉）。所以止血時要記下關閉的時間，1 小時內決定下一步。

第二件是退路不只一種。開關沒效、又修不好，先關新服務的開關、再打開報名服務 worker 的開關；回復版本則是先停舊、再起新，新舊行程不重疊。

## 上線後的第一週

打開新服務的開關之後，每天同一個時間看一次，第一場約 2 萬人的活動送完之後再看一次。指標與告警見本章〈[可觀測性與韌性](06_observability_resilience.md)〉，名稱照服務：

| 看什麼 | 正常 | 不對勁代表 |
| --- | --- | --- |
| `reminder.deliveries` 的 SLI：`sent / (sent + failed + expired + missed)` | 每天都在 SLO 之內 | `missed` 不為 0：服務停過超過 1 小時；`failed`、`expired` 增加：供應商或資料有問題 |
| `reminder.scan.duration` | 與壓測的結果同一個量級 | 明顯更慢：壓測的假設與現場不符，回到本章〈[壓測與調校](08_load_test_tuning.md)〉 |
| `reminder.overdue.unsent` | 每批結束後回到 0 | 一直大於 0：送不完，或卡住了 |
| `reminder.deliveries{result="skipped"}` | 0 | 別的寫入者先寫了紀錄：舊 worker 的開關還開著，或多起了一個實例 |
| `runtime.goroutines`、`runtime.heap.bytes` | 批次之間回到原本的水位，看斜率，不看數值 | 持續上升：第 15 章的事故重演，照 runbook |
| 日誌 `shutdown deadline passed` | 沒有 | 發布時關機等不完：期限比最壞的一則還短 |

## 舊 worker 什麼時候刪

上線之後，舊 worker 的開關是關的，程式還在報名服務裡，是回復的退路。下面全部成立才刪：

- 新服務完整送過至少一場約 2 萬人的活動，並走完一個 SLO 的窗口，SLI 都在 SLO 之內（第 9 章〈[SLI 與 SLO](../chapter9/08_sli_slo.md)〉）。
- 舊 worker 的開關從上線起一直是關的，沒有用它回復過，`skipped` 一直是 0。
- runbook 與上線計畫的回復，已經改成沒有舊 worker 的版本：關新服務的開關，或回復提醒服務的版本。
- 刪除是報名服務 repo 的一個 PR：舊 worker 的程式、設定開關與測試一起刪，照第 13 章的標準 review。

刪完，ADR-0019 的內文不動；第 15 章行動項目 3「遷移另開 issue」的那張 issue 結案。

## 取捨

這集的取捨都來自前面各章的判斷湊在一起：

- **刪舊 worker 是整個上線裡最難回頭的一步。** 第 13 章說難以回頭的要特別嚴格，而退路本身就是事故的原因：舊 worker 和報名 API 共用行程。留得越久，報名服務多背一天第 15 章的風險，行動項目 1 的逾時與並行上限只降低機率；刪得太早，回復只剩關開關與回復提醒服務的版本，後者要走一次部署，單一實例還得先停舊、再起新。上面的條件是在兩邊取一個點；場次少的平台，窗口走完可能比活動來得早，要決定的是等活動，還是接受較長的空窗。
- **止血的開關不是免費的。** 關開關保護了服務，也讓時鐘開始走：關著超過 1 小時，到期的提醒打開後就是失敗。1 小時內修得好，沒有損失；修不好，是拿提醒換服務的穩定，這是事故指揮官的決定，runbook 只能讓值班的人看得見時鐘，不能替他選。
- **檢查表全標「擋」，就是第 13 章的「什麼都擋」。** 每次上線都要全套證據，下一次沒人當真，所以放行的三項要寫出來、有人簽。第一次上線與改動「上線與回復」順序時走全表；只改一個預設值的發布，重驗它碰到的那幾項就夠。
- **壓測是推算，不是保證。** 它只在那台機器、那組參數下成立，縮小規模的結果推到現場是假設。檢查表擋的是「沒有證據」；真正的驗證是第一週的 `reminder.scan.duration` 與 SLI，兩者合起來才算數。

什麼都不查就上線，在沒有外部副作用、重跑無害的內部工具（例如產生報表）上是合理的。提醒服務送出去的推播撤不回，記為失敗的不補寄，所以才需要這張表。

## 重點整理

- 檢查表每項一行，連到談過它的集，附一個別人能檢查的證據：連結讓人知道缺了去哪補，證據讓人知道有沒有做。
- 擋的是兩類：收回的本事（開關演練、回復順序、告警與 runbook、值班的人）、收不回的後果的防線（端對端測試、壓測、秘密與符號層級的弱點）；其餘放行、開 issue、有人簽。
- runbook 回頭連結第 15 章，只改診斷位址（`127.0.0.1:6060`）、開關（`REMINDER_SEND_ENABLED`）與影響；開關關著超過 1 小時，到期的提醒打開後記為失敗。
- 第一週看 SLI、`reminder.scan.duration`、`reminder.overdue.unsent`、`skipped`（應為 0）、goroutine 與 heap 的斜率。
- 舊 worker 是退路也是風險，走完 SLO 的窗口、`skipped` 為 0、沒有用它回復過、runbook 已改，才刪。
