# 設計文件

## 本集目標

把一個元件從行程裡拆出去之前，判斷設計文件要先決定哪幾件事：資料歸屬、上線與回復的順序、單一實例的取捨；並把決定記成取代舊決定的 ADR。

## 情境

虛構的活動報名平台（平台、事故與數字都是教材範例，文中的人一律用角色稱呼）上，提醒 worker 先跑在報名服務的行程內。供應商變慢時，卡住的 goroutine 讓報名服務的容器超過記憶體上限被終止，報名 API 部分失敗約 30 分鐘。事後檢討把「拆成獨立部署，開新 ADR 取代 ADR-0012」列為行動項目 3，負責的是提醒 worker 的作者，完成的定義是新 ADR 合併、遷移另開 issue（第 15 章〈[事後檢討（blameless postmortem）](../chapter15/04_blameless_postmortem.md)〉、〈[行動項目與追蹤](../chapter15/05_action_items.md)〉）。

這集是那份設計文件與 ADR-0019。每一段怎麼寫，第 14 章〈[結構：背景、目標、非目標、方案、取捨](../chapter14/02_doc_structure.md)〉談過，這集只看這份文件要做的決定。本集沒有程式碼：套件與 API 本章〈套件結構與 API〉會談，寄送紀錄表與唯讀檢視本章〈錯誤與資料層〉會談，關機本章〈並行〉會談，開關的設定與演練本章〈建置與發布〉、〈上線檢查表〉會談。

## 設計文件：提醒服務

下面是 review 之後、宣告「已決定」的版本，精簡成一頁。

```markdown
# 提醒服務：把提醒 worker 拆成獨立部署

狀態：已決定（採唯讀檢視、單一實例）
日期：2030-06-03
reviewer：維護者、行動 App 團隊、值班工程師
決策者：產品負責人

## 背景

提醒 worker 與報名 API 共用行程。ADR-0012 把這個風險記為接受的取捨，理由是獨立部署要多維運一個單元；
事故顯示代價比當時估計的大。提醒的行為不變：活動開始前 24 小時寄出、每人每場最多一次、預定時間後 1 小時內寄出；
推播供應商限制每秒 50 次，一場最多約 2 萬人，每 5 分鐘掃描一次。管道是 email 與推播，兩個一起搬。

## 目標與非目標

目標：worker 出問題不再影響報名服務；上面的行為與「寧可不寄，也不重複」不因拆分打折；上線與回復的每一步都能退回。
非目標：多副本與選主；補寄超過期限的提醒（行動項目 5，另案）；正式環境的資料遷移步驟（上線計畫只寫順序與回復）；
報名服務的修改，唯讀檢視除外。

## 資料歸屬

- 提醒服務擁有寄送紀錄表：schema、migration 與寫入都歸它，「活動 + 報名者」的唯一限制在這張表上。
- 報名資料只透過報名服務擁有的唯讀檢視讀取，欄位是活動、報名者、裝置 token、email、活動開始時間。
- 檢視是兩個服務之間的契約，由報名服務的 migration 維護；改欄位等於改契約，要先通知提醒服務。
- 提醒服務不寫報名資料，也不直接讀報名服務的表。

## 替代方案

| | 好處 | 不選的理由 |
| --- | --- | --- |
| 不拆，只靠逾時、並行上限與開關 | 不新增部署單元 | 共用行程的風險還在，逾時與上限只降低它發生的機率 |
| 報名服務提供 API | 資料庫結構不外露 | 每輪要拉最多 2 萬人的名單，報名服務得為此加分頁與容量；API 慢了提醒跟著慢，批次又拖慢報名 API |
| 訊息佇列 | 時間到才處理，不必掃描 | 要新增並維運佇列，取消報名要撤回已排入的工作（ADR-0012 的理由仍在） |

## 上線與回復

1. 新服務以開關關閉的狀態部署，確認能啟動、讀得到檢視。
2. 關掉報名服務裡 worker 的開關。
3. 打開新服務的開關。

回復反過來：先關新服務的開關，再打開報名服務 worker 的開關。任何時刻最多一邊開著。

## 風險

- 兩邊同時打開時，唯一限制擋得住重複，但兩邊會互搶同一批提醒。
- 只跑一個副本。唯一限制是第二道防線，不是多副本的設計；服務停著就沒有人寄，停超過 1 小時，就趕不上「預定時間後 1 小時內寄出」的目標。
- 多一個要部署、監控與值班的單元。
```

資料歸屬這一段寫的是決定，不是資料表長什麼樣；欄位與索引留在程式碼與 migration。替代方案只寫好處與不選的理由，怎麼比較才公平，第 14 章〈[替代方案怎麼寫](../chapter14/04_alternatives.md)〉談過；「不拆」放進表裡當基準：行動項目 1（逾時與並行上限）做完之後，它才是需要認真比較的選項。

## 哪裡會衝突

每一段單獨看都合理，湊在一起才出現的取捨有三個：

- **唯一限制擋得住重複，擋不住互搶。** 寄之前先寫紀錄、靠唯一限制擋重複，是第 10 章〈[冪等性](../chapter10/03_idempotency.md)〉談過、第 14 章〈[設計文件的 review](../chapter14/05_design_review.md)〉問過的設計。拆成兩個服務之後，兩邊的開關同時打開不會多寄，但兩邊搶同一批提醒，出事時分不出是哪一邊在寄、該關哪一邊。開關本來是維運細節（第 12 章〈[設定與環境變數](../chapter12/08_config_env.md)〉），現在成了兩個服務之間的協調機制，所以順序要寫進上線計畫，回復也照同一條規則反過來走。
- **寧可空窗，不要重疊。** 關掉舊的、打開新的之間，有一段沒有人在送。目標是預定時間後 1 小時內寄出，掃描每 5 分鐘一次，幾分鐘的空窗用得起；重疊用不起。
- **單一實例的可用性預算是那 1 小時。** 唯一限制只擋重複，不分配工作，多副本只會互搶，所以只跑一個。代價是單點：服務停著，重啟後下一輪才接著掃，停超過 1 小時，就趕不上「預定時間後 1 小時內寄出」的目標。發布新版本時新舊行程重疊，等於兩個副本，同樣要先停舊、再起新。多維運一個單元的成本，要和「多快救得起來」一起算。

## ADR-0019：取代 ADR-0012

決定記成一則 ADR，只摘「一年後有人問為什麼」會用到的東西（第 14 章〈[設計文件與 ADR 的關係](../chapter14/06_design_doc_and_adr.md)〉）。它與 ADR-0012 放在同一個目錄，例如 `docs/adr/0019-reminder-service-split.md`（虛構的路徑，指的是報名服務的 repo）：

```markdown
# ADR-0019：提醒改由獨立部署的提醒服務送出

狀態：已接受（2030-06-10）
取代：ADR-0012
設計文件：「提醒服務：把提醒 worker 拆成獨立部署」（連結）

## 背景

ADR-0012 讓提醒 worker 跑在報名服務的行程內，後果記了共用行程的風險，理由是獨立部署要多維運一個單元。
事故中 worker 的 goroutine 累積，報名服務的容器被終止，報名 API 部分失敗約 30 分鐘；風險的代價比當時估計的大。

## 決定

提醒由獨立部署的提醒服務送出，只跑一個副本。提醒服務擁有寄送紀錄表，報名資料只透過報名服務擁有的唯讀檢視讀取，
欄位是活動、報名者、裝置 token、email、活動開始時間。提醒的規則不變：預定時間後 1 小時內寄出，每人最多一次，寧可不寄，也不重複。
上線依序：新服務以開關關閉部署、關掉報名服務裡 worker 的開關、打開新服務的開關；回復反過來。

不採用：不拆；報名服務提供 API（每輪要拉最多 2 萬人的名單，兩個服務互相拖慢）；訊息佇列（要新增並維運佇列，取消報名要撤回已排入的工作）。

## 後果

- worker 出問題不再影響報名服務。
- 多一個要部署、監控與值班的單元。
- 檢視成為兩個服務之間的契約，改欄位要先通知提醒服務。
- 單一實例：服務停著就沒有人寄，停超過 1 小時，就趕不上「預定時間後 1 小時內寄出」的目標。多副本與選主不在這個決定內。
```

ADR-0012 的內文一個字不動，只改狀態那一行：

```diff
-狀態：已接受（2030-03-04）
+狀態：已被 ADR-0019 取代（2030-06-10）
```

這與 ADR-0012 後果裡那條「worker 與報名服務共用行程」對得上：舊的 ADR 留下當時接受了什麼，新的 ADR 的背景指出哪個條件變了，下一個讀者不必猜它是疏忽還是取捨。

## 取捨

- 拆分的成本是真的。ADR-0012 選不拆，理由是維運只有一個人；現在的判斷是共用行程的代價更大。若逾時、並行上限與開關已經讓風險夠小，不拆仍然可以是對的。
- 唯讀檢視讓提醒服務綁在報名服務的資料庫上：資料庫停了，提醒也停；檢視改了，提醒跟著壞。API 與佇列把耦合移到網路與基礎設施。平台已經有人維運佇列、或報名服務願意為提醒維護 API 時，值得重新評估。
- 單一實例省下協調多副本的複雜度，換來單點。放大的瓶頸本來就是供應商的每秒 50 次（第 14 章〈[設計文件的 review](../chapter14/05_design_review.md)〉談過），多副本不會更快，只會更需要協調。
- 設計文件與 ADR 各有成本：文件要 review，ADR 要寫。切換的步驟與正式環境的資料遷移，一頁放不下，另寫上線計畫，文件只留順序與回復。

## 重點整理

- 拆出元件要先決定：資料歸屬（誰擁有紀錄表、讀對方的資料走什麼契約）、替代方案（API、訊息佇列、不拆）、上線與回復的順序、單一實例的取捨。
- 唯讀檢視是兩個服務之間的契約：報名服務的 migration 維護它，提醒服務只讀、不寫。
- 唯一限制擋得住重複，擋不住互搶：兩邊的開關不能同時打開，順序寫進上線計畫，回復反過來；寧可空窗，不要重疊。
- 單一實例的可用性預算是預定時間後的 1 小時；多副本與選主是非目標。
- 決定記成 ADR-0019 取代 ADR-0012；舊的內文不改，只改狀態行。
