# 一個服務從設計到上線

前 15 章教的是一個一個分開的判斷：套件怎麼切、錯誤怎麼設計、測試測哪一層、goroutine 歸誰管、逾時怎麼分配、指標怎麼取、關機要等什麼、映像怎麼建、事故怎麼處理。真正寫一個服務時，這些判斷會同時出現，而且互相影響：逾時預算和關機期限要一起算，並行上限和供應商的限流是兩件事，SLO 的告警和業務的告警要分工，設定開關、版本和回復的順序要配合。每一塊都照做了，組在一起才發現互相衝突；上線前不知道還缺什麼，只能靠「應該可以了」。

這一章把這些判斷組成一個服務，從設計文件一路做到上線檢查表。服務是第 15 章事故之後拆出來的「提醒服務」：虛構的活動報名平台原本把提醒 worker 跑在報名服務的行程內，對推播供應商的呼叫沒有逾時與並行上限；供應商變慢時，goroutine 不斷累積，報名服務的容器因記憶體超過上限被終止，報名 API 部分失敗約 30 分鐘，關掉 worker 的設定開關才止血。事後檢討的行動項目 3，就是把 worker 拆成獨立部署（第 15 章〈[事後檢討（blameless postmortem）](../chapter15/04_blameless_postmortem.md)〉、〈[行動項目與追蹤](../chapter15/05_action_items.md)〉）。沒讀過第 14、15 章也讀得懂，本章〈設計文件〉會交代背景。每集只談服務的一層，重點是這些判斷湊在一起時哪裡會衝突、怎麼取捨；已經教過的做法回頭連結，不重講。服務的程式碼放在 `examples/chapter16/`，各集引入需要的片段；壓測與 profile 的輸出是實際跑出來的，標明平台與 Go 版本。平台、事故與數字都是虛構的教材範例，文中的人一律用角色稱呼。
